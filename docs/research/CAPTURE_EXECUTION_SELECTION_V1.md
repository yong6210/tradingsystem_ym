# 수집 실행 경로와 전체 회귀 기준 v1

2026-09-18. 실행 전 [고정 설정](../../configs/research/capture_execution_v1.json)에 경로, 검사 목록, 부하 조건과 채택 조건을 등록했다. 이 설정은 연구 검증 도구가 읽으며, 거래 서버나 기존 앱의 실운용 기본값을 자동으로 바꾸지 않는다.

## 경로 선택

| 역할 | 진입점 | 선택 이유와 범위 |
|---|---|---|
| 수집 기반의 주 개발 경로 | `app.research.data.guarded_generation_capture.run_synthetic_capture` | 같은 연결을 유지한 저장 세대 전환, 압축·정리, 증분 감사, 실패 후 정리를 함께 검증한다. `QueuedTransport`만 허용하는 합성 전용이다. |
| 향후 짧은 공개 연결 확인 | `app.research.data.bounded_parent_capture.run_bounded` | 부모 감사 저장 단계500ms 제한을 수집 종료 후에도 검사한다. 원본을 삭제하지 않는 유한 구간 경로다. 이번 등록에서 공개 실행은 비활성이다. |
| 역사적 비교·회귀 | 이전 segmented/sealed/retained/rolling/archived 실행기 | 기존 증거와 reader를 보존한다. 검사에서는 제외하지 않지만 실운용 기본안으로 채택하지 않는다. 특히 구간마다 재연결하는 rolling 방식은 이미 품질 공백 때문에 제외했다. |

주 개발 경로는 최신 sealed 경로의 단순 상위 버전이 아니다. 사용하는 감사 작업자와 자료 형식이 다르므로, 지난 수정이 모든 실행기에 자동 적용됐다고 표현하지 않는다. 실제 공개 transport를 세대 실행기에 연결하는 일은 별도 통합 단계다.

기존 최대120초·16세대·대기2세대·세대별62단위·부모 동기 작업500ms 제한을 유지한다. 합성 세대 runner의 저장 예약0은 실제 운용 예약16GiB를 충족했다는 뜻이 아니다. 검증 실행 전 실제 여유 공간을 확인하고, 운용 정책과 단위 검사의 명시적 모의를 구분한다.

## 결과를 보기 전에 고정한 기준

[등록 기록](../../reports/validation/selected_capture_20260918/registration.json)에 검증 당시880개 소스/설정 해시와 검사 목록을 기록했다. 연구424개·실행814개, 고유1,238개이며 기존 항목 제외·자동 재시도는0이다. 다음 기준은 결과에 따라 바꾸지 않는다.

- 등록된 모든 검사는 정확한 ID로 실행한다. 실패·오류·건너뜀·미실행이 하나라도 있으면 해당 전체 회귀 통과를 승인하지 않는다. 최신 선택 경로 관련109개는 부분집합이며 전체 개수에 중복 가산하지 않는다.
- 연구 검사는 기존 Python3.12 환경, 실행 검사는 기존 Python3.14 환경에서 순차 실행한다. 파일/CPU 경합을 만들지 않도록 두 집합과 부하 시나리오를 동시에 실행하지 않는다.
- 주 경로에서 정상40초/20입력과 높은 입력18초/200입력을 각각 한 번 실행한다.8초 세대 전환·0.5초 봉인·방향별1000호가 레벨을 유지한다. 높은 입력이 실패해도 조건을 낮추거나 통과할 때까지 반복하지 않는다.
- 같은 자료의 gzip 재생·독립 원본 재생·live 감사17항목, 수신 후 저장 건수, 전체 저장량·예약·작업자 정리를 대조한다. 단위/파일 수 및 bytes는 실제 생성 자료에서 측정하며 하루 값으로 단순 확대하지 않는다.
- 기존8개 저장/정리/감사 anchor 지점에서 선택 경로의 실제 부모를 SIGKILL한다. 별도 프로세스의 복구·재복구 내용 동일, 기존 파일 변경0, 원래 구간 보존을 검사한다.
- 소스가 등록 후 바뀌면 실행을 거부한다. 완전 자동매매·24시간 등록·새 모델 채택은 위 검사 통과만으로 허가되지 않는다.

도구: [전체 회귀 실행기](../../scripts/verify_capture_regression.py), [선택 경로 부하·강제 종료 실행기](../../scripts/verify_selected_generation_capture.py). 과거 비교용 verifier의 검사 로직은 재사용하고 runner만 명시적으로 선택한다. 기존 verifier 소스는 수정하지 않는다.

## 장기 운용 전 남은 자원 계약

현재 세대/단위/개별 문서 상한은 유한하지만 하루 이력의 총비용을 승인하는 계약은 아니다. 아래를 구분해 명세·사전 심사·실측을 연결해야 한다.

| 자원 | 현재 확인할 수 있는 제한 | 다음 필수 검증 |
|---|---|---|
| 저장 bytes | 공용 capture 예산, 임시 파일·예약 비용, 개별 metadata8MiB | 하루 원본·압축·seed·proof·임시 중복의 전체 비용 및 물리 여유. 비교 보고서/독립 원본 사본은 capture 밖의 검증 비용으로 별도 집계. |
| 파일·목록 |16세대/세대62단위의 유한 실행, startup `reconcile`이 기존 파일 목록을 순회 | 총 파일 수·부모 inventory 항목 수 제한, 이력 증가 시 부모 작업량과 시작 시간. |
| 감사 상태 | 이전 proof에서 현 세대만 감사, processor/reducer seed 저장 | seed/interval 상태의 최악 크기와 장시간 입력 분포. 수익/품질에 유리하도록 누락 자료를 버리지 않을 것. |
| cold 복구 | 원점부터 세대와 원본/gzip을 확인하는 read-only 복구 | 전체 이력 재생량·시간·메모리의 상한, 오래된 손상 탐지, 취소/시간 초과 시 미완료 상태 유지. |
| 대기열/CPU | 대기2세대·작업자/예약 제한·부모500ms | 정상 및 burst에서 서비스 속도와 대기열 여유, 장기 CPU/저장 지연. 한도를 올려 backlog 실패를 숨기지 않을 것. |

이 계약을 마친 뒤 공개 transport 통합·짧은 공개 확인·장기 수집 등록을 판단한다. 그 다음 실제 체결/시장가 전환 비용과 고정 후보 전진 모의 검증으로 돌아간다. 이번 경로 선택은 매매 전략 선택이나 수익성 검증이 아니다.
