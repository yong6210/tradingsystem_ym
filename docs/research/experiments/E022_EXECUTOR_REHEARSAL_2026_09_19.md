# E022 — 예약 실행기 전체의 오프라인 리허설

**예약에 고정한 실행기를 수정하지 않고 네 가지 합성 시나리오에서 끝까지 실행했다. 네 가지 모두 사전에 정한 동작과 일치했다.** 실제 네트워크 요청0, 예약된 공개 실행은 아직 미시작이다. 기존85개 검사를 다시 수행하거나 실제 거래 표본을 추가한 결과가 아니다.

## 이번에 확인한 빈틈

이전 검사는 시간 경계·입력 상태 전이·원장 감사를 각각 확인했다. 이번에는 `scripts/run_signal_window.py`의 실제 `execute()`를 호출해 대기 → 준비 조회 → ARM → 주기별 공개 입력 처리 → 진입 → 종료 → 원문 재생/독립 감사까지 함께 실행했다.

외부 HTTP 응답과 시계만 합성으로 교체했다. 상태 전이·진입/청산 코드·SQLite 저장·원문 파일 저장·입력 재생·Decimal 감사는 원래 구현을 그대로 사용했다. 실제 소켓 연결을 막았고 호출되지 않았음을 확인했다. 운영체제 장애·실제 API 장애·실제 네트워크 지연 시험은 아니다.

총203개는 **합성 요청**이다. 네트워크 호출 수나 공개 시장 표본으로 집계하지 않는다. 정상/청산 불가 사례의 합성 진입은 한국05:01:02.900에 발생했고, 예정05:01 이전 체결은 없었다. 정상 사례의 종료 청산은 전략 고유 청산과 분리됐다.

네트워크 시작 후 합성 활성 시간은 최대153.4초로 기존180초 한도 이내였다. 시작 전 모의 대기60초를 포함한 시계 진행213.4초와 구분한다. 실제 컴퓨터에서 그 시간만큼 관측한 결과가 아니다.

각 모의 응답과 SQLite 입력, 상태/출력 재생, 원문 호가에 대한 독립 Decimal 가격·수수료·현금 계산, 목표 의도의 시각 계보 검사가 통과했다. 종료 청산이 불가능한 경우에도 원장 검사가 통과하는 이유는 **미청산 상태를 정확히 보존했기 때문**이다. 원장 통과가 청산 성공이나 운영 적격성을 뜻하지 않는다.

## 중요한 판단

이번 범위에서는 예약 실행을 막을 새로운 코드 결함을 재현하지 못했다. 따라서 실제 예약에 묶인 소스·설정·시각을 변경하지 않았다. 사전에 보호한 소스/과거 자료/예약 준비 증거 **858개 파일**은 전후 동일했다. 기존 예약 `btc-4`도 유지했다.

반면, 최우선 호가 수량이 부족하면 이번 모의 모델이 포지션을 정리하지 못할 수 있다는 한계는 실제 전체 실행에서 확인했다. 이를 가상의 더 깊은 체결로 없애지 않는다. 앞으로 공개 결과를 읽을 때는 다음을 따로 판단해야 한다.

- 대상 신호가 실제로 관측됐는지, 진입이 적격이었는지.
- 펀딩/자료 오류 때문에 진입이 차단됐는지.
- 청산이 전략/위험 조건 때문인지, 관측 종료 때문인지.
- 종료 시 남은 모의 포지션이 있는지. 남았다면 청산 완료로 보고하지 않는다.

실제 거래소 주문·부분체결·보호주문·포지션 대조는 여전히 미구현/미검증이다. 이 합성 결과로 실제 계좌 운용을 시작하지 않는다. 최종 전략의 수익성·다양한 장세 대응력 역시 확인된 것이 아니다.
