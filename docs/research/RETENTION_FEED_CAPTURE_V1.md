# 압축 보관 상태를 구분하는 재시작 감독기 v1

2026-09-18. [현재 우선순위](CURRENT_PRIORITIES.md)의 첫 항목 중 **완료된 capture의 보관 전환과 감독기 복구 연결**을 구현했다. 수집 중 활성 journal의 구간 삭제·장기 기록 회전은 아직 아니다. 기존 고정 코드와 자료는 보존하고 `RetentionFeedCapture`를 별도 API로 추가했다.

## 해결한 문제

기존 `RestartableFeedCapture`의 중단 복구는 원본 파일이 존재한다고 가정한다. 한편 `closed_capture_retirement`는 검증한 압축본과 계획을 남기고 새 합성 원본을 지울 수 있다. 이 둘을 구분하지 않고 연결하면 원본이 정상적으로 전환된 것인지, 이유 없이 유실된 것인지 판단할 수 없다.

새 감독기는 종료 결과와 보관 전환 계획을 연결하는 등록 파일을 capture 밖의 공용 run 저장소에 남긴다. 호출자가 별도 보관한 handle은 그 파일의 hash를 포함한다. 재개 시 등록·완료 결과·작업 anchor·계획·gzip·삭제 의도/완료 기록을 모두 대조한다. 하나라도 다르면 원본 경로로 우회하거나 시장 연결을 시작하지 않고 거부한다.

## 처리 순서와 경계

1. 새 감독기 생성 시 opt-in mode를 고정한다. 각 capture를 시작할 때 원장/시장 자료보다 먼저 원본 보관 정책을 등록한다. capture 안 `storage.json`은 공용 계약의 신원 사본이다. 별도 예산을 만들지 않으며 모든 파일·예약은 상위 `ReservedStorageBudget` 하나로 계산한다.
2. `prepare_closed_retention(index)`는 감독기가 종료됐고 대상 시도의 정상 종료 결과가 원장에 기록된 경우만 허용한다. [비용 사전 심사](RETIREMENT_ADMISSION_V1.md)에 추가 등록 파일의 비용까지 포함한다. 불리한 전환은 파일 변경 없이 거부한다.
3. 유리한 경우 기존 전환 준비를 수행하고 등록 파일을 원자적으로 저장한다. 이 호출은 원본을 삭제하지 않는다. 반환한 최신 handle을 별도로 저장해야 한다. 테스트 harness는 파일과 부모 디렉터리를 fsync한다. 외부 보관은 다른 호스트 백업을 뜻하지 않는다.
4. `resume`은 원본/의도/완료 상태를 검증하고 gzip으로 메모리에서 처음부터 재생한다. 검증 자체는 새 파일을 남기지 않는다. 원본이 없어도 등록과 의도가 일치해야 한다. 원본이 다시 생겼거나 등록이 없으면 보존하고 정지한다.
5. `run`이 호출되면 모든 등록을 먼저 검증한 뒤 기존 v1 삭제·fsync·완료 프로토콜을 이어간다. 다시 cold replay한다. 원본 없는 완료 시도를 옛 raw 복구 함수에 넘기지 않는다. 등록 없는 일반 수집 중단은 기존 복구 및 새 세션 경로를 사용한다.
6. 반복 실행/새 owner로 재개해도 영수증·압축본·체크포인트 파일이 늘지 않는다. 과거 audit 결과와 품질 판정은 유지하며 복구한 과거 시장 상태를 실시간 processor로 사용하지 않는다.

기존 감독기 이벤트 형식, 120초 원래 창, 같은 부팅·시계 계약, 최대 시도/작업 수, 연결 전 deadline 검사와 소스 binding은 유지했다. 상속한 생성·검증·요약 동작과 별도로 `run`의 작은 조정 루프를 버전 파일에 명시적으로 두었다. 고정 v1을 수정하거나 숨은 hook 부작용으로 capture 생성을 바꾸지 않았다. 향후 공통화는 새 계약과 회귀 검증을 거쳐야 한다.

## 실제 강제 종료 시험

[고정 시험 계획](../../reports/validation/retention_supervisor_20260918/drills_final/plan.json), [4개 결과](../../reports/validation/retention_supervisor_20260918/drills_final/summary.json), [종합 검증](../../reports/validation/retention_supervisor_20260918/verification.json).

새 합성 capture에 대해 다음 4곳에서 실제 부모 프로세스를 SIGKILL했다.

| 중단 지점 | 재개 시 확인 |
|---|---|
| 외부 handle 저장 직후 | 원본 보존 상태를 확인하고 등록한 전환을 실행 |
| 삭제 의도 임시 파일 fsync 직후 | 미완료 임시 파일을 보존하고 정상 의도/완료 기록 생성 |
| 원본 unlink 직후 | 의도와 압축본으로 정당한 원본 부재를 확인하고 완료 |
| 완료 임시 파일 fsync 직후 | 원본을 재생성하지 않고 완료 기록 확정, 임시 파일 보존 |

모든 사례에서 재개 후 연결/스냅샷 요청 0, gzip 전용 감사 의미 17개 항목 일치, 원래 수집 창/합산 품질 판정 유지, 같은 owner 및 새 owner 반복 재개 시 파일 내용/개수 불변을 확인했다. 이 fixture의 수집 창은 0.45초다. 24시간 수집 또는 다양한 실시장 부하를 증명하지 않는다.

신규 18개 테스트에는 부정 등록·압축 손상·의도 없는 원본 유실·원본 재등장·과거 handle·mode 누락 거부, 비용 거부의 무변경, 등록 저장 실패, 일반 중단 복구 경로 유지가 포함된다. 기존 953개와 합쳐 고유 971개를 검증한다. 최종 검사 수와 통과 여부는 종합 검증 기록을 따른다.

초기 개발 시험 18개는 통과했다. 이후 자체 검토로 `original_deletion` 상태를 완료 영수증 수가 아니라 실제 원본 부재로 판단하도록 고쳤다. 원본 unlink와 완료 영수증 사이에도 삭제 사실을 정확히 보고하기 위한 수정이다. 초기 SIGKILL harness는 JSON에서 읽은 list와 실행 중 tuple의 직접 비교에서 실패했다. 정규화된 JSON 바이트 비교로 고쳤으며 초기 로그/소스/부분 자료를 보존했다. 초기 시험을 최종 성공 사례 수에 합산하지 않는다.

## 남아 있는 제약

- **준비/등록 도중 최신 외부 handle을 얻기 전에 끊기면 자동 채택하지 않는다.** 미등록 계획이나 기존 handle에 없는 등록 파일이 있으면 원본·임시 파일을 보존하고 오프라인 점검을 요구한다. 이 경우까지 무인 자동 복구한다고 주장하지 않는다.
- 기존 자료에 새 정책을 소급 등록하지 않는다. 이전 감독기를 이 API에 조용히 이전하거나 소스 hash 검사 범위를 줄이지 않는다.
- 외부 handle 저장 호출은 harness/호출자 책임이다. 자동 서비스·오프호스트 백업·동시 비협조적 파일 변경·전원 손실 인증은 없다.
- 기존 정상 경로 비용 심사는 지속 재생 2회 비용을 보수적으로 포함한다. 새 감독기의 복구 재생은 메모리에서 수행해 파일이 추가되지 않는다. 장애 임시 파일은 실제 공용 공간에 남으며 별도 집계한다. 무한한 장애 반복의 저장 상한은 보장하지 않는다.
- 큰 입력/0.1초 구간에서 관측한 대기열 초과를 이번에 해결한 것으로 세지 않는다. 전체 수집 창 최대 120초와 24시간 미등록을 유지한다.

다음은 활성 journal에서 원본/압축 위치와 인계 상태를 함께 추적하는 계약, 유한 원장/체크포인트 회전, 대기열 부하 검증이다. 이후 실제 공개 연결과 더 긴 기술 시험을 판단한다. 새 전략·수익성 검증·실주문은 이번 범위에 없다.
