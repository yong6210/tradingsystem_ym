# 통합 수집 장애·재시작과 적격 구간 감사 v1

2026-09-17. [구간 감사기](../../app/research/data/feed_coverage_audit.py), [오프라인 통합 훈련](../../scripts/run_feed_coverage_drill.py), [검사](../../tests/test_feed_coverage_audit.py), [검증 기록](../../reports/validation/feed_coverage_recovery_v2_20260917/verification.json).

**완료 범위는 저장·처리 경계의 장애 검증과 기록에 근거한 적격 시간 계산이다.** 새 전략이나 수익률을 평가한 작업은 아니다. 구간은 당시 기록된 상태와 신선도 만료 규칙으로 계산하며, 관찰 사이에 기록되지 않은 장애가 없었다는 증명으로 해석하지 않는다. 모든 결과에 `continuous_runtime_coverage_certified=false`를 남긴다.

## 무엇을 막았는가

- 원본이 저장됐다는 이유만으로 당시 처리 완료·사용 가능 시각까지 복원하지 않는다. 원본 순번·해시와 일치하고 같은 엔진으로 정확히 재현되는 처리 감사 배치가 있어야 한다.
- 마지막 정상 관찰 이후를 종료 시각까지 정상으로 채우지 않는다. 다음 검증된 관찰까지만 계산하고, 그 사이 신선도 만료 시각이 오면 먼저 끊는다.
- 연결 종료나 처리 오류를 수신한 뒤 처리·공개까지 걸린 시간을 정상으로 남기지 않는다. 해당 수신 시각부터 배치 공개 시각까지 모든 조건에서 보수적으로 제외한다.
- 재시작했다고 원래 수집 시작·종료 시각을 새로 잡지 않는다. 재시작 공백·처음 준비 시간·끝의 미관측 시간은 원래 달력 분모에 남긴다.
- 저장 확정 전 원본 꼬리 또는 처리 감사 유실을 정상 복구로 숨기지 않는다. 검증 가능한 앞부분은 진단용으로 남기되 해당 실행의 품질 입력은 거절한다.

## 구간 생성 규칙

이 도구는 **종료돼 변경되지 않는 기록을 사후 감사**하는 용도다. 실행 중 계속 쓰이는 감사 파일을 동시에 읽어 품질 인증하는 인터페이스가 아니다. 원본의 전체 확정 prefix를 먼저 검증하고, 순서대로 연결되는 처리 감사 배치를 재생한다. 같은 배치의 첫/마지막 순번, 원본 연결 해시, commit 시각, 관찰 시각과 모든 관찰 필드가 일치해야 한다.

시작·종료 시각은 호출자가 원래 계획으로 전달하며 각 epoch의 첫 `RUN_WINDOW`와 대조한다. 서로 다른 epoch를 합칠 때 원래 창·시계 영역이 같고, epoch 식별자가 중복되지 않으며, 감사 관찰 구간의 순서가 맞아야 한다. 동일 호스트의 이번 부모·자식 프로세스는 공통 단조 시계를 사용했다. **시계 영역 문자열을 같게 넣는 것만으로 재부팅 전후·다른 호스트의 시각을 합칠 수는 없다.** 재부팅 간 시각 대응은 미구현이다.

각 검증된 관찰은 공개 시각부터 아래 만료 시각까지 유효한 상태를 제공한다. 실제로 인정하는 끝은 다음 검증 관찰·원래 종료·만료 시각 중 가장 이른 시각이다. 마지막 관찰에는 다음 점이 없으므로 이후 구간을 생성하지 않는다.

| 조건 | 만료·무효 조건 |
|---|---|
| L2 | depth 수신 시각+1초와 장부 사용 가능 시각+1초 중 먼저 도달하는 시각 |
| market 연결 | 마지막 유효 market 수신+3초, 연결 종료 |
| mark | 마지막 유효 mark 수신+3초, 연결 종료 |
| 감시·시계 | 마지막 감시 수신+500ms, 기록된 지연·시계 오류 |
| 영속 원본 | 검증된 commit 경계 뒤의 기록 상태; 마지막 감사 관찰 이후는 추정하지 않음 |

오류 누적·중단·원래 종료 이후에는 새 적격 구간을 만들지 않는다. OPEN/END/FAULT/STOP 및 새 처리 오류의 수신→공개 구간을 제외한다. 이를 다섯 조건에서 교집합하고 [고정 달력 검사](FORWARD_DATA_CONTRACT_V1.md)에 전달한다. 임의의 0 오류 카운터를 실제 무결성 증명으로 쓰지 않으며, 감사 오류·미확정 원본 꼬리·처리 오류가 있으면 별도의 `EPOCH_AUDIT_OR_PROCESSOR_FAILURE`로 품질 입력을 거절한다. 이 감사기는 모든 장애 유형의 운영 통계 생산기를 대신하지 않는다.

원본 확정 prefix 자체가 손상됐으면 해당 epoch의 구간을 만들지 않는다. 감사 파일이 없거나 잘렸거나 내용이 바뀌면 마지막 검증 배치까지만 남긴다. 뒤늦은 원본 재생으로 원래 온라인 처리 시각을 새로 만들어 채우지 않는다. 이 검증은 같은 엔진의 재현성 검사이며 독립 거래소 원장 검산이나 체결 확률 검증은 아니다.

## 강제 종료·복구 훈련

시장 메시지는 고정한 모의 값이며 실제 네트워크를 연결하지 않았다. 파일 fsync·commit/관찰 시각과 자식 프로세스 SIGKILL은 실제 로컬 실행이다. [최종 통합 결과](../../reports/validation/feed_coverage_recovery_v2_20260917/drill_summary.json):

| 종료 지점 | 확인 결과 |
|---|---|
| 원본 append 뒤, commit 전 | 미확정 꼬리를 보존하고 실패로 표시. 마지막 검증 관찰 뒤는 미확인 |
| 원본 commit·처리 뒤, 감사 쓰기 전 | 확정 원본 1개에 대응하는 감사 유실을 탐지. 처리 시각을 복원해 채우지 않음 |
| 감사 행 절반을 기록·fsync한 뒤 | 잘린 감사 행을 보존하고 앞의 완전한 배치까지만 인정 |
| 감사 행 전체 fsync 뒤 | 두 배치를 정확히 재생하되 마지막 관찰 뒤부터 재시작 준비 구간을 제외 |

네 경우 모두 자식 종료 코드 -9, 기존 원본·감사 파일의 바이트 해시 불변, 기존 journal의 실시간 장부 재사용 거절을 확인했다. 새 journal·새 epoch로 시작하고 호가·mark가 없는 초기 관찰은 부적격이었다. 새 snapshot·depth 연결·mark·감시 이후에만 복귀했다. 모든 실행에서 원래 10초 창을 유지했고, 처리 감사 유실·미확정 꼬리가 있는 앞선 epoch의 실패는 다음 정상 epoch로 지워지지 않았다.

별도 훈련에서 market와 public 채널을 차례로 종료·재개했다. 연결만 다시 열어서는 정상화되지 않으며 market에는 새 mark, public에는 새 snapshot과 연결되는 depth가 필요했다. 종료 수신과 처리 사이에 의도적으로 둔 20ms도 제외됐다. **이는 저장·처리 계층의 모의 연결 경계 검증이며 실제 소켓 장애·자동 재접속 성능 검증은 아니다.**

[첫 실행](../../reports/validation/feed_coverage_recovery_20260917/drill_summary.json)도 보존했다. 이후 미확정 원본 꼬리를 명시적 감사 오류로 분류하고 이를 검사하는 사례를 추가했다. 당시 세 소스 버전도 첫 실행의 `source_snapshot`에 보존했다. 첫 실행과 보완 후 실행을 합쳐 이번 작업에서 실제 SIGKILL 8회, 최종 버전 검증은 4회다. 모든 실행에서 새 네트워크 요청·비공개 요청·주문은 0건이다.

## 기존 실제 수집 자료에 적용한 결과

| 항목 | 결과 |
|---|---:|

**이는 실제 연속 가동률이나 지정가 체결률이 아니다.** 기존 193/205개의 정상 시점 관찰을 단순 비율로 계산하지 않았다. 12초는 등록 예정인 24시간과 다르고, 진단상 공동·시간대 비율도 정책 문턱에 미달하므로 `QUALITY_INPUTS_REJECTED`다. 짧은 시작 준비 구간이 포함된 결과로 장기 신뢰성을 추정하거나 문턱을 완화하지 않았다. 기존 관측을 재분석했으며 새 실시간 시장 표본은 추가하지 않았다.

## 검증과 다음 순서

신규16개 포함 관련424개 검사 통과. 기존 동결 코드·산출물 해시 대조1,057건, 고유788경로 모두 일치했다. 신규 검사는 만료 시각, 지연된 종료·호가 오류, 미확정 꼬리, 감사 유실·잘림·변조, 원본 손상, 두 epoch의 원래 분모 유지, 시계 영역/창/epoch 혼용 거절을 포함한다. 구간 차감은 별도의 정수 집합 계산과도 대조했다. 프로세스 종료 훈련은 로컬 파일 시스템 범위이며 정전·디스크 고장·다중 호스트 복구 보장이 아니다.

```bash
python3 -m unittest tests.test_feed_coverage_audit
python3 scripts/run_feed_coverage_drill.py --output reports/validation/NEW_UNIQUE_DIRECTORY
```

다음은 **실제 수집기의 유한 재연결 예산·고정 종료·감사 기록 영속화 정책을 연결하는 작업**이다. 이어 대기열·저장 용량·감시 지연의 부하 검증을 수행하고, 소스/복구/용량/시계/전체 관측 이력을 묶어 24시간 기술 시험 등록 가능성을 판단한다. 수집 재시작 감독자, 호스트 재부팅 시각 대응, 자동 경보 전달과 장기 메모리·처리량 한도는 미완료다.

24시간 기술 시험은 아직 시작하지 않았고 전략 채택도 없다. 기술 자료 적격성 이후에 체결·비용 모형과 전진 모의 평가를 진행해야 한다. 계좌 관측 생산기·실제 조건부 주문 대응·공통 진입 위험 예산 등 운용 완료 조건도 별도로 남아 있다.
