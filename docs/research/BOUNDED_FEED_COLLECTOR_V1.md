# 유한 재연결·고정 종료·감사 영속화 v1

2026-09-18 KST. [수집 감독자](../../app/research/data/bounded_feed_collector.py), [공개 전송 어댑터](../../app/research/data/public_feed_transport.py), [실행기](../../scripts/probe_bounded_feed.py), [수집 검사](../../tests/test_bounded_feed_collector.py), [전송 검사](../../tests/test_public_feed_transport.py), [검증 기록](../../reports/validation/bounded_feed_v3_20260918/verification.json).

**완료: 공개 데이터 수집의 재시도 예산, 새 세션·스냅샷 복구, 원래 종료 시각 유지, 배치별 감사 저장 확인, 실패별 중단 분류.** 최대120초의 기술 검증 실행기다.24시간 수집·실주문·체결 검증·새 전략 채택은 시작하지 않았다. 첫 실제 실행에서 긴 루프 지연이 있었으며 그 원인의 완전한 규명과 장시간 용량 검증은 남아 있다.

## 재연결과 종료 규칙

1. 실행 시작·종료 단조 시각, UTC 시작, 시계 영역, 소스 해시, 진단용 의도적 종료 여부를 `plan.json`에 저장한다. 출력 경로는 새 디렉터리만 허용하며 기존 자료를 덮지 않는다.
2. 원본 로그와 감사 파일의 저장 확인을 선행한 뒤 공개 소켓을 연다. 저장 사전 검사에서 실패하면 네트워크를 열지 않는다. 비공개 URL·키·계좌·주문 인터페이스는 없다.
3. 네트워크 단절·네트워크 시간 초과만 자동 복구 대상으로 분류한다. 실행 전체 재시도 대기는 정책의1·2·4·8·16·30초, 최대6회다. 연결이 잠시 정상이 되어도 예산을 초기화하지 않는다. 최초 시도를 포함해 최대7개의 수집 epoch를 만들 수 있다.
4. 한 채널의 단절도 현재 epoch 전체를 끝낸다. 새 journal·새 epoch·새 public/market 연결·새 snapshot으로 재개하며 이전 호가·mark·감시 상태를 재사용하지 않는다. 양쪽을 함께 다시 연결하는 보수적 방식이므로 연결 공백과 요청 수가 늘어나는 비용이 있다.
5. 다음 재시도 대기까지 포함해 원래 종료 시각에 도달하면 더 시도하지 않는다. 예약된 타이머가 늦게 깨어나도 종료 시각을 재검사한다. 연결·REST 작업은 원래 남은 시간으로 제한하고, 전송 계층도 초기화 뒤 요청 직전에 다시 검사한다.
6. 저장 실패, 파싱/순서/신선도 감시에서 누적된 처리 오류, 시계 오류, HTTP 거절, 종료 정리 실패는 전체 실행을 중단한다. HTTP429/418과 리디렉션도 자동 반복하지 않는다. 처리 오류를 새 epoch로 갈아 끼워 지우지 않는다.
7. 장애를 감지하거나 의도적으로 연결 종료를 결정한 시각에 STOP 수신 시각을 고정한다. close 응답 대기를 정상 시간으로 추가하지 않는다. 종료 중 수신은 `CLOSING_WS`로 보존하고 판단 상태에는 반영하지 않는다. 저장 자체가 실패해 보존할 수 없는 프레임은 별도 누락 개수와 실패 상태로 남긴다.
8. 종료·재시도 소진 후 남은 시간도 원래 달력 분모에 남긴다. 짧게 관찰한 구간으로 전체 분모를 줄이지 않는다. 기존 [구간 감사기](FEED_COVERAGE_RECOVERY_V1.md)에 각 epoch를 원래 창 그대로 전달한다.

비동기 대기는 취소하지만, 운영체제 지연·동기 디스크 작업·인터프리터 정지까지 강제 선점하는 실시간 시스템은 아니다. **원래 종료 이후의 사용 차단과 새 요청 전 검사**를 검증한 것이며 프로세스의 물리적 종료 시간이 항상 정확히 그 시각이라는 보장은 아니다. 닫기와 사후 감사는 관찰 창 이후에도 진행될 수 있다.

## 감사 기록과 메모리

각 배치에서 원본 commit→처리 관찰 생성→감사 행 쓰기→fsync를 수행한다. 파일 생성 시 디렉터리도 sync한다. 감사 fsync가 실패하면 해당 행을 완료로 세지 않으며 이후 재시도를 중단한다. 파일에서 읽히는 바이트와 저장 완료 응답은 구분한다. 사후에 감사 행을 읽을 수 있더라도 수집 감독자의 실패 판정은 품질 거절 사유로 유지한다.

감사 파일은 epoch당32MiB, 감독 기록은 실행당4MiB로 제한한다. 원본64GiB 예산은 이전 epoch 사용량을 빼서 다음 epoch에 넘기므로 재연결 때 초기화되지 않는다. 디스크 여유16GiB를 검사한다. 이 수치가 실제24시간 처리량에 충분하다는 입증은 아직 없다.

저장한 배치를 메모리에 계속 쌓지 않고 집계와 마지막 저장 순번만 유지한다. 수신 루프는 매 프레임 뒤 다른 작업에 실행 기회를 넘겨, 이미 채워진 소켓 대기열을 계속 읽느라 감시·flush·종료 작업이 밀리는 경우를 방지한다. 기존 원본 대기2,048개 상한을 유지한다. 전체 호가 장부 크기, 입력률 대비 처리량, 디스크 지연과 backpressure의 가격 신선도 영향은 다음 부하 검증 대상이다.

감사 행의 `published_ns`는 내부 처리 관찰 시각이며 감사 fsync 이후 실제 주문에 사용된 시각을 의미하지 않는다. 이 실행기는 주문을 발행하지 않는다. 구간 계산은 기록된 상태와 유효 시간에 따른 모형이며 연속 정상 가동·대기열 체결의 인증이 아니다.

## 실제 실행 이력과 확인된 한계

모든 실행을 보존했다. 각 관찰 창은 원래12초이며 수동으로 창을 늘리지 않았다. 아래는 단계별로 보완한 소스 버전의 실제 공개 실행이다.

| 실행 | 결과 | 공개 WS / REST |
|---|---|---:|
| [첫 실행](../../reports/validation/bounded_feed_20260918/collection_result.json) | REQUEST 뒤 약9.06초 동안 기록 진행이 멈췄고 감시 지연 오류로 중단. snapshot·의도적 재연결까지 도달하지 못함 | 2 / 1 |
| [두 번째 실행](../../reports/validation/bounded_feed_v2_20260918/collection_result.json) | 수신 루프 양보·REST 단계 시각 기록 추가 후 재연결1회와 원래 종료 확인 | 4 / 2 |
| [최종 실행](../../reports/validation/bounded_feed_v3_20260918/collection_result.json) | 전송 직전 종료 재검사·의도적 연결 종료 시점 차단까지 보강 후 재연결1회와 원래 종료 확인 | 4 / 2 |

세 실행 합계 공개 WS10회·REST5회, 실주문0·비공개 요청0이다. 첫 두 실행의 당시 소스7개를 각각 `source_snapshot`에 보존했다. 성공한 실행만 골라 과거 실패를 없애지 않았다.

**첫 실행의9초 지연을 수신 루프 하나의 원인으로 확정하지 않는다.** 원본에는 REQUEST→다음 수신 사이의 긴 공백만 남아 정확한 정지 지점을 확정할 단계 계측이 없었다. 수신 루프의 실행 기회 독점 가능성은 별도 코드 검토와 버스트 검사로 보완했다. 이후 REST 계측에서 import·클라이언트 생성·헤더·본문 시각을 기록했지만, 나중의 빠른 실행만으로 최초 현상의 원인을 입증할 수는 없다. 초기화·부하·디스크·스케줄링 지연 분석을 다음 완료 조건으로 남긴다.

관측 최대값은 지연 상한 보장이 아니다. 모든 시도 시작은 원래 종료 시각 이전이었고, 두 epoch의 첫 `RUN_WINDOW`는 같은 시작·종료를 가리킨다. 첫 epoch STOP의 수신 시각은 의도적 종료 결정 시각과 일치했다. 새 epoch에서도 새로운 자료로 적격 시점 관찰이 발생했다.

기록·만료 규칙상 공동 적격 시간은8.535459042초(약71.1288%), 최장 미확인·부적격 구간은3.011397125초다. 의도적 재연결과 준비 공백을 포함한 진단이며 **실제 연속 가동률·체결률·전략 성과가 아니다.**24시간 길이와 공동/시간대 문턱을 충족하지 못해 `QUALITY_INPUTS_REJECTED`다.130/150을 가용률로 계산하지 않는다.

[관측 이력](../../reports/validation/bounded_feed_v3_20260918/inspection_history.json)은 실패 후 저장하지 못한 프레임까지 고려해 전체 실행 완료 뒤 UTC를 보수적인 관측 종료 상한으로 기록했다. 향후 전진 등록은 이전 모든 관측 이력과 합쳐야 하며, 기존 동결 정책의 관측 종료 시각을 그대로 최신이라고 사용하면 안 된다.

## 검사와 재현

신규32개와 기존424개, 관련456개 검사 통과. 기존 동결 코드·산출물 해시1,188건(고유919경로) 일치. 연구 검사는 NumPy가 있는 기존 번들 Python, 신규 수집·전송 검사는 httpx/websockets가 있는 프로젝트 `.venv`에서 실행했다. `.venv`에서 전체를 한 번에 실행한 시도는 NumPy 미설치로 시작 단계에서 실패했으며 해당 로그도 보존했다. 운영/연구 의존성을 함께 재현하는 검사 환경 정리는 남아 있다.

검사 범위에는 재시도6회 소진, 정상 연결 후에도 예산 유지, 늦게 깬 타이머, 연결/REST 취소, 저장 사전 검사, 감사 fsync 오류, 전송 오류와 저장 오류의 동시 발생, 잘못된 메시지, 새 epoch 자료 확인, 과도한 버스트, 종료를 넘긴 HTTP 초기화, HTTP 거절/리디렉션 차단이 포함된다.32개는 모의·로컬 검사이고 실제 공개 실행 결과는 위 표로 구분한다.

```bash
.venv/bin/python -m unittest tests.test_bounded_feed_collector tests.test_public_feed_transport
.venv/bin/python scripts/probe_bounded_feed.py --output reports/validation/NEW_UNIQUE_DIRECTORY --seconds 12 --reconnect-drill
```

CLI 관찰 창은5~120초다. `--reconnect-drill`은 첫 snapshot 이후3초에 현재 수집 epoch를 종료해 소켓을 닫고 같은 재시도 경로를 검사한다. 실제 거래소 장애를 재현하거나 강제로 발생시키는 기능은 아니다. 프로세스가 종료된 뒤의 자동 재시작 감독자도 아직 없다.

## 다음 우선순위와 종료 조건

다음은 **저장·대기열·초기화 지연의 부하 검증**이다. 원본·감사 합산 저장량과 여유 공간, fsync 지연, 대기열 상한, 큰 입력률/느린 저장/초기화 지연 상황에서의 감시·중단·원본 보존을 측정한다. 최초9초 지연과 같이 설명되지 않은 정지가 남아 있으면 장기 운용 준비 완료로 판정하지 않는다.

이어 소스·복구·용량·시계·전체 관측 이력을 묶어24시간 기술 시험의 등록 여부를 판단한다. 현재 동결 정책은 여전히 미등록이고 이 실행기로24시간 요청은 거절된다. 실제 계좌 증거·조건부 주문 대응·공통 진입 위험 예산·외부 경보·프로세스 재시작 운영과 체결/비용 모형·전진 수익성 평가는 각각 별도의 미완료 조건이다.
