# 재연결과 과거 기록 감사 분리 v1

2026-09-18. Binance BTCUSDC 공개 데이터의 **최대120초 기술 확인용** 수집기 v5다. 전략 채택·실주문·24시간 시험 등록은 계속 차단한다. 기존 v1~v4와 검증 자료는 보존했다.

## 문제와 변경

v4는 연결 종료 → 종료된 epoch 전체 감사 → 재시도 대기 → 새 연결 순서였다. 이전 고정 합성1시간 자료만으로도 감사12.19초가 필요해 재연결 공백을 늘렸다. 빠른 감사기로 교체하는 것만으로는 긴 기록의 동기 실행 문제가 없어지지 않는다.

v5는 종료된 epoch의 감사를 별도 Python 프로세스에 맡기고 원래 재시도 시각에 재접속한다. raw/audit 작성자는 닫힌 뒤에만 읽기 작업을 제출한다. 제출 당시의 두 checkpoint SHA256, 작업 번호, 원래 시간 창·시계 영역을 요청/응답에 결합한다. 기존 잠금 유지 snapshot 감사기가 모든 기록을 재생한다. 새 시장 상태는 기존대로 새 세션/snapshot에서 시작한다.

이 비동기 감사는 거래 승인 신호가 아니다. 모든 epoch의 감사 완료 전에는 전체 자료를 통과시키지 않는다. 이전 epoch의 오류가 다음 연결 중에 발견되면 그 발견 시각으로 STOP을 기록하고 연결/REST 대기를 취소한다. 재시도 대기 중이면 다음 연결을 막고, 원래 종료 후 발견돼도 전체 결과를 거부한다. 실패 후 감사가 생략된 epoch도 `AUDIT_SET_INCOMPLETE`로 드러난다. 전역 저장 실패 뒤에는 새 감사 요청/결과 파일 저장을 하지 않는다.

## 고정 경계

| 항목 | 경계/동작 |
|---|---|
| 동시 감사 | 자식 프로세스1개 |
| 미완료 작업 | 실행 중 포함2개, 초과 시 수집 실패 |
| 누적 작업 | 최초+6회 재시도의 최대7개 |
| 작업 시간 | 대기열에 들어간 시점부터15초 |
| 최종 감사 대기 | 최대15초 후 작업 취소·프로세스 kill/reap |
| IPC | 응답1개2MiB, 누적 응답8MiB, stderr16KiB, 요청16KiB |
| 구간 집계 | 감사기10,000개 경계; 초과는 잘라서 통과시키지 않고 거부 |
| 자식 메모리 | RSS 최고 사용량384MiB,50ms 주기 감시+완료 시 검사 |
| 원래 수집 창 | 최대120초, 재접속/감사로 연장하지 않음 |
| 저장 | 원본·감사·감독·계획·결과가 기존 공통 예산/공간 보존 정책 사용 |

RSS 경계는 OS의 강제 할당 제한이 아니다. 감시 사이의 초과와 커널/호스트 정지를 막는다는 보장은 없다. IPC 경계도 직렬화된 바이트 수이며 Python 객체의 실제 메모리가 정확히8MiB라는 뜻이 아니다. 구간 수·작업 수·응답 길이와 자식 수를 함께 제한한다. 소켓 정리는 기존 최대2초 close 정책을 유지하고, 감사 종료 뒤 자식 회수를 기다린다. 정상 스케줄링/kill 가능한 로컬 프로세스에서 검증했으며 커널 정지 상황의 절대 종료 시간을 보장하지 않는다.

## 확인 결과

- 신규 경로50개 + 기존 연구424개 + 기존 실행/저장/재생154개 = 고유628개 검사 통과. 취소 중 생성되는 자식의 소유권, stdout/stderr 폭주, 잘못된 응답/시간 창/checkpoint, 프로세스 종료·멈춤, 감사 누락·메모리 경계·저장 실패까지 포함한다.
- 별도 보존한 오프라인 훈련3개 통과: 감사를 대기시켜도 재접속, 재접속 뒤 감사 실패가 현재 epoch 중단, 최종 대기 만료 후 kill/reap. 마지막 훈련은 빠른 오류 주입을 위해 대기 한도를150ms로 낮췄다. 공개 운용의 기본값15초와 구분한다.
- 공개12초 확인: 재접속1회, WS4회·REST snapshot2회, 원본442개·감사136개, 두 epoch 감사 완료. 오류0, 자식 프로세스 회수 완료, 실제 주문0.
- 공개 작업의 제출→완료는77.39ms/102.92ms, 자식 최대 RSS24.20MiB였다. 원본·감사·부가 파일의 공통 예산 사용량599,153bytes. 이 짧은 입력률을 장기 최대치로 간주하지 않는다.
- 같은 공개 기록을 기존 compact 감사기로 다시 읽었을 때 JSON 표현 기준 모든 필드가 일치했다. IPC의 tuple→list 변환을 맞추기 위해 JSON 왕복 변환만 했으며 제외한 필드는 없다.
- 이전 검증 사슬1,943건/고유1,674경로의 해시가 일치했다. 새 공개 관측 상한은 별도 inspection history에 이전 이력과 함께 연결했다.

공개 확인의 기록상 공동 적격 시간은12초 중8.4755초(70.6293%)다. 계획된 재접속 공백도 원래 분모에 남겼다. 전체 품질 판정은 `QUALITY_INPUTS_REJECTED`이며24시간 길이/품질 계약을 통과한 것으로 해석하지 않는다. 실제 공개 확인에서는 감사가 빠르게 끝나 대기열 최고1개였다. 느린 감사와 재접속의 겹침은 별도의 오류 주입 훈련으로 입증했다.

## 남은 순서

1. **저장 여유와 입력률 상한**을 먼저 결정한다. 이번 물리 여유는16GiB 보존분 위 약15.74GiB이고, 이전60초 관측의2배 단순 연장인 하루20.43GiB에도 못 미친다. 사용자 자료를 임의로 삭제해 해결하지 않는다.
2. 큰 호가 장부·버스트·실제 fsync와 감사의 동시 부하에서 큐/RSS/감시 지연/복구를 검증한다. 작은 장부의 정상 종료만으로 상한을 선언하지 않는다.
3. 장시간 수집 전에는 감사 작업을 닫힌 segment 등 더 작은 단위로 나누거나 별도 고정 정책을 검증해야 한다. 이전 하루 합성 전체 재생185.67초는 현재 작업 한도15초를 초과하므로 **v5의120초 제한을 풀어 하루 실행하면 안 된다.** 이후에만24시간 기술 시험 등록 가능 여부를 재판단한다.

이번 완료 범위는 재연결의 동기 감사 의존성 제거와 실패 전파 검증이다. 모든 장세에서 작동하는 전략 또는 수익성의 증명은 여전히 아니다.
