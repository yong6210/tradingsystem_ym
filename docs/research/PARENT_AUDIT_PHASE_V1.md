# 부모 감사 저장 단계의 독립 지연 검사 v1

2026-09-18. [공간 확보 후 회귀](../../reports/validation/storage_recovery_20260918/REPORT.md)의 두 실패를 분리했다. 부모 감사 단계의 지연 감시 누락을 고정 조건으로 재현하고 별도 sealed collector 경로를 보완했다. 재연결은 실제 저장/재생과 모델링한 조정기 시계로 누적 회계·늦은 재시도 거부를 확인했다.

## 확인한 결함과 수정

기존 `BackgroundIncrementalAudits`는 전체 작업 제한시간을 검사한다. 반면 부모의 검증·checkpoint 저장이500ms를 넘었는지는 수집 중 watchdog이 감지할 것에 의존한다. `collect_epoch`가 종료해 watchdog이 사라진 뒤 pipeline이 남은 감사를 처리하면, 전체 작업 제한 내의600ms 동기 저장 지연을 성공으로 인정할 수 있다.

시험은 하나의 고정 sealed 단위를 준비하고 `end_epoch`를 명시적으로 호출한 다음 checkpoint 디렉터리 fsync 이후0.6초를 주입한다. 기존 경로는 이를 성공으로 받아들이고, 새 경로는 실패로 차단한다. 이전 전체 실행의 hook 시점이 저장되어 있지 않아 **그 실패와 정확히 같은 스케줄이었다고 단정하지는 않는다.** 독립적으로 재현한 실제 감시 결함이다.

`app/research/data/bounded_parent_audit.py`의 `BoundedParentAudits`는 자식 응답 후 부모의 검증·저장·확인 단계에 별도의500ms 시계를 적용한다. 검증 후, 각 저장 hook 후, 성공 결과 공개 직전에 검사한다. 작업 전체 timeout과 자식 프로세스/예약/취소/원본 검증 계약도 유지한다. 동기 저장 호출 자체를 중단시킬 수는 없고, 반환 시 초과를 감지해 실패로 전환한다.

`app/research/data/bounded_parent_capture.py`는 해당 작업자를 사용하는 `BoundedParentPipeline`과 별도 `run_bounded` 진입점을 제공한다. 기존 기본 경로·동결된 구현은 바꾸지 않는다. 최신 세대 실행기는 다른 작업자를 사용하며 이미 자체 `_phase` 검사를 가진다. 이번 수정이 모든 수집 실행기에 자동 배포됐다는 뜻은 아니다.

파일이 rename된 뒤 지연을 감지하면 파일은 존재할 수 있다. 성공 결과는 공개하지 않고 owner/budget 실패를 유지하며, 명시적인 기존 successor 복구는 가능하다. 파일을 되돌리거나 삭제해 성공처럼 보이게 하지 않는다. 새 경로의 실제 collector 종료 후 주입 검사에서는 `FATAL_FAILURE`, 품질 거부, 결과 저장 없음, 예약0·잠금 해제를 확인했다.

## 재연결 실패의 분리

이전 검사는1.6초 안에 두 epoch가 생성된다는 전제에서 누적 회계를 검사했다. 한 번만 생성된 사실은 두 번째 epoch에서 예산이 초기화됐다는 증거가 아니다. 현재 자료로는 최초 실패 순간의 지연 원인까지 복원할 수 없다.

`tests/test_fixed_reconnect_accounting.py`는 조정기 시계·sleep 완료·epoch 종료 사건만 모델링한다. 실제 journal·공유 예산·원본 재생·결과 저장을 사용하고, epoch 원본 기록 시계는 실제 시계를 유지한다. 전송 요청은0,60초 namespace는 실제60초 수집이 아니다. 운영 기간·재시도1초·공간16GiB·감시 한도는 변경하지 않는다.

1. 여유가 있는 재시도: 같은 예산 객체로 두 epoch를 만들며 앞 파일 hash가 유지되고 실제 전체 저장량과 집계가 일치한다.
2. 종료500ms 전에 실패:1초 재시도는 원래 종료 시각을 넘으므로 두 번째 epoch를 만들지 않는다.
3. 허가한 재시도가 원래 종료 시각에 깨어남: 허가 이력은 유지하지만 두 번째 epoch를 만들지 않는다.

이 세 분기가 통과했다. 오래된1.6초 실제 시간 검사의 안정성까지 해결됐다고 부르지 않는다. 공개 재연결 품질 인증도 아니다.
