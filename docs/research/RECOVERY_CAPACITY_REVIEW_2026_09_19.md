# 회복 비교에 명시적 수량 한도 연결

기존 연구용 `Capacity` 입력 형식을 재사용해 회복 비교에 예비 자금·최대 총수량·역행 시 전체 손실 한도를 연결했다. 새 `review_capacity`는 수량 상한을 계산할 뿐 주문을 승인하지 않는다. 방향·자리·반응·미체결·펀딩 검사는 수행하지 않으며 실제 주문 컨트롤러에 연결하지 않았다.

결과: `reports/validation/recovery_capacity_examples_20260919/review.md`와 `review.json`.

## 계산 방식

요청 수량, 체결 가능 수량, 최대 총수량의 잔여분, 예비 자금을 제외한 증거금 여유, 각 역행 시나리오의 전체 손실 한도 중 가장 작은 값을 구하고 주문 수량 단위로 내림한다. 최소 주문 수량·금액을 만족하지 못하면 실행 가능한 추가 상한은 0이다.

역행 손익에는 이전 실현손익과 비용, 이번 증가의 진입 비용, 가정 종료 시의 수수료·스프레드·슬리피지를 포함한다. 기존 `assess_increase`의 스트레스 산식과 완전히 같은 것은 아니다. 기존 함수는 종료 수수료를 포함하지만 이번 비교처럼 종료 가격 마찰까지 반영하지는 않는다. 기존 주문 알고리즘을 조용히 교체하지 않고 별도 검토 함수로 두었다.

## 17:55 예시

실제 계좌 정보는 없으므로 다음은 민감도 검증용 가정이다. 기존 단순 증거금 여력 6,819.79 USDC, 요청 0.15 BTC, 체결 가능량 0.15, 최대 총수량 0.3을 놓았다. 남길 자금·손실 예산은 아래 네 조합만 시험했으며 사용자 승인값이나 추천값이 아니다.

| 남길 자금 | 전체 손실 예산 | 계산상 추가 상한 | 제약 | 전체 회복 가격 |
| ---: | ---: | ---: | --- | ---: |
| 3,000 | 500 | 0.053 BTC | $3,000 역행 손실 | 63,234.6 |
| 3,000 | 750 | 0.121 BTC | 증거금 여유 | 63,179.2 |
| 5,000 | 500 | 0.053 BTC | $3,000 역행 손실 | 63,234.6 |
| 5,000 | 750 | 0.057 BTC | 증거금 여유 | 63,230.0 |

회복 가격을 가장 낮추는 수량이 곧 선택 수량은 아니다. 어떤 한도를 명시했는지에 따라 계산상 상한이 달라지고, 이 범위 안에서도 시장 근거가 불충분하면 추가 판단은 남는다. 남길 여력을 낮추거나 손실 예산을 높여 원하는 물량에 맞추는 방식으로 해석하지 않는다.

## 미확정 상태 처리

실제 한도가 없으면 `capacity_quantity=None`으로 남긴다. 스냅샷이 오래됐거나 미래 시각이어도 수량을 내지 않는다. 미정과 실제 계산 결과 0을 구분한다.

기존 보유만으로 이미 가정 손실 예산을 넘었다면 추가 상한을 0으로 만든다. 이것은 새로운 노출을 더할 여력이 없다는 계산이며 자동 손절·전량 청산·방향 전환 지시는 아니다. $2,000~3,000은 역행 시나리오이지 손절 가격이 아니다.

## 검증과 남은 차이

신규 테스트 5개 통과: 한도·예비 자금 보존과 주문 미승인, 미입력·오래된/미래 정보 거부, 기존 손실 초과 시 추가 0, 유동성·최소 주문 제약, 숏의 상방 역행 적용. 실제 예시 네 조합에서도 추가 후 남길 자금과 종료 비용 포함 손실 한도를 확인했다. 입력·코드 해시를 저장했다. 실주문 0건이다.

실제 계좌·주문 예약·유동성 입력과 한도 승인은 여전히 없다. 다음 구현 검토는 기존 수량 심사와 이번 보수적 종료 비용 산식의 차이를 동일 입력으로 대조하는 것이다. 두 계산을 동시에 사용하면서 서로 다른 추가 상한을 내는 상황을 먼저 정리해야 한다.
