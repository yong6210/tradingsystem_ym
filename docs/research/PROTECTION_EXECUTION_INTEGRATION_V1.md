# 보호 주문 원장·모의 전송 연결 v1

2026-09-17. **오프라인 주문 제어 검증 완료. 실계정 연결이나 전략 수익성 검증이 아니다.** 기존 감독기와 실험 소스는 보존하고 새 조정기를 추가했다.

## 이번에 연결한 범위

[보호 감독기](PROTECTION_SUPERVISOR_V1.md)의 현재 요구 → 불변 명령 예약 → 전송 직전 재검사 → 원자적 점유 → 명시적으로 주입한 모의 전송 → 응답/조회 대조 → 체결 증분 저장을 연결했다.

- `STOP`: 고정 손절가, 현재 포지션의 반대 방향, 필요한 미보호 수량. MARKET 수량 필터와 가격 tick을 검사한다. 이는 모의 의미 계약이며 Binance 실제 조건부 주문 요청 형식이 아니다.
- `EXIT`: 손절/위험 위반/보호 거절 시 현재 청산 예약을 뺀 잔여 수량. 일반 지정가의 3초를 기다리지 않는다.
- `CANCEL`: 진입 잔량, 잘못된 보호 주문, 포지션 종료 후 남은 주문을 대상으로 한다. 취소 명령의 응답만으로 원 주문의 최종 상태나 체결량을 추정하지 않는다.

모든 STOP/EXIT는 reduce-only 의미만 가진다. 실제 API 요청 어댑터는 없으며, 현재 코드를 라이브 client에 바로 연결해서는 안 된다. 범위는 단방향 포지션·주기별 scope·계좌별 단일 writer다.

## 중복·오래된 상태 방지

1. 감독기의 요구 저장과 명령 예약 사이에 종료되면 요구에서 복구한다. 명령 예약 도중 오류는 명령·계획 감사 기록을 함께 롤백한다.
2. 송신 전 `READY → SENDING`을 커밋한다. 이후 응답이 없거나 프로세스가 종료되면 기존 ID를 조회한다. 조회 결과 없음도 재송신 허가로 쓰지 않는다.
3. 전송 직전 최신 조정 포지션, 1초 이내 관측, 현재 요구 수량, 가격/수량 규격, 다른 불명 주문을 다시 확인한다. 기존 예약 수량이 너무 크면 폐기하고 새 관측으로 다시 계획한다.
4. STOP/EXIT 응답을 반영한 뒤에는 더 새로운 전체 포지션/주문 관측이 있어야 다음 수량 명령을 만든다. 종료된 부분 체결 이후에도 저장된 옛 포지션을 다시 청산하지 않는다.
5. 누적 체결량은 감소할 수 없다. 같은 버전의 상충 응답, 잘못된 scope, 초과 체결, 종료 상태 변경을 거부한다. 체결 증분은 응답과 같은 트랜잭션에서 저장한다.
6. `NEW`/전송 성공은 보호 완료가 아니다. 감독기에 신선한 ACTIVE 보호 상태가 들어와야 보호 수량으로 센다. 보호 거절/만료는 중단 사유로 영속화하고 다음 조정에서 비상 청산을 요구한다.
7. 외부 관측이 flat이어도 이 원장에 불명/활성 명령이 남아 있으면 `cycle_reconciled=false`다. 종료 응답 뒤 새 전체 관측까지 있어야 주기 종료를 확인한다.

`decision.phase`는 감독기가 전달받은 스냅샷만 평가한 값이다. 호출자는 조정기의 `execution_phase`, `outstanding_commands`, `cycle_reconciled`도 함께 사용해야 한다. 예를 들어 외부가 flat이라고 해도 자체 전송 결과가 불명확하면 실행 상태는 `FLAT_COMMAND_RECONCILIATION_REQUIRED`다.

## 검증 결과

[검증 기록](../../reports/validation/protection_execution_integration_20260917/verification.json), [테스트 로그](../../reports/validation/protection_execution_integration_20260917/tests.log), [7단계 모의 훈련](../../reports/validation/protection_execution_integration_20260917/drill.json).

- 새 조정기 19개, 자료 점검기 3개를 포함한 관련 266개 테스트 통과.
- 실제 자식 프로세스를 송신 직전과 모의 접수 직후 강제 종료했다. 직전 종료는 불명/조회 유지, 접수 후 종료는 같은 ID 조회로 복구했고 추가 송신은 없었다.
- 7단계 훈련: 부분 진입 `.003 BTC` → 잔량 취소 → 보호 거절 → 재시작/위험 중단 유지 → 비상 청산 `.001`만 체결 후 만료 → 새 관측으로 나머지 `.002` → flat/종료 대조.
- 모의 접수 4건(CANCEL, 거절 STOP, EXIT 두 건). 별도 모의 거래소 DB의 체결 합 `.003 BTC`와 원장의 증분 합 `.003 BTC` 일치. 실주문·계정 조회·외부 통지 모두 0.
- 모의 체결은 지정한 테스트 응답이다. 실제 체결률·슬리피지·성과의 증거로 사용하지 않는다.

## 여전히 해결해야 할 운영 위험

| 남은 위험 | 현재 행동 | 다음 구현·종료 조건 |
|---|---|---|
| 전체 스냅샷의 누락/늦은 관측 | 입력의 `reconciled`와 증가 버전을 신뢰 | 일반 시장가 전환·보호 주문·실제 체결을 하나의 계좌 조정기가 대조하고 순서 역전/누락을 거부 |
| 불명 주문과 비상 청산의 충돌 | 중복 송신을 막고 조회 유지 | 조회 불가·보호 공백을 운영 경보/복구 절차와 연결. 통신 장애 중 즉시 청산 성공을 보장하지 않음 |
| 실제 조건부 주문/조회·취소 경로 | 모의 STOP 의미 계약만 존재 | 공식 API 의미를 별도 버전 어댑터로 정규화; 사용자 데이터/REST 경합 검증 |
| 취소 거절·시장가 거절 반복 | 같은 취소 의도 자동 재생성 안 함; 더 새 관측에서 EXIT 다시 계획 가능 | 재시도 횟수·간격·영구 거절 분류/격리 정책 필요. 현재 디스패처를 무제한 반복 루프로 실행하지 않음 |
| 최소 수량 미만 잔여 포지션 | 임의 올림 없이 CONTRACT 차단 | 실제 거래소의 잔여 포지션 청산 규격을 확인하고 별도 처리 |
| 중복 worker·계좌 공통 예약 | 단일 writer 전제 | 일반 fallback과 보호 경로의 공통 원자적 예약/대조, 필요 시 계좌 리더 잠금 |
| 필터·계정 조건과 경보 전달 | 명시적 계약 fixture, 감독기 로컬 경보 | 현재 필터의 신선도/계정 모드/허용 수량·외부 경보 전달 성공을 검증 |
