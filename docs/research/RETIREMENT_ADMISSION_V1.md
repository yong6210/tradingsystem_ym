# 종료 자료 보관 전환의 비용 사전 심사 v1

2026-09-18. 대상은 사전에 보관 전환 정책을 등록한 새 자료이며, 기존 사용자/시장 관측 자료의 원본은 변경하지 않는다. 이번 결과는 저장·재생 기술 시험이다. 전략 성과나 24시간 운용 인증이 아니다.

## 문제와 변경

[종료 자료 보관 전환 v1](CLOSED_CAPTURE_RETIREMENT_V1.md)의 작은 시험은 원본을 지웠어도 계획·영수증·재생 기록 때문에 전체 capture 크기가 늘었다. 삭제량만으로 절감 효과를 판단할 수 없다. `retirement_admission.py`는 준비 기록을 만들기 **전에** 그 기록의 실제 직렬화 크기를 계산한다. 기본 조건은 정상 종료 경로에서 capture가 최소 1바이트 줄어드는 것이다. 원하는 최소 절감량을 더 크게 지정할 수 있으나, 이번 시험에서 수익률이나 결과에 맞춰 임계값을 탐색하지 않았다.

- `forecast_retirement`: 원장·원본·등록 gzip·기존 감사 상태를 검증하고, 새 메모리 상태로 gzip을 재생한다. 새 파일/디렉터리 생성과 원본 삭제는 없다. 기존 잠금 및 fsync는 사용한다.
- `prepare_if_economic`: 불리하면 `anchor=None`으로 끝낸다. 유리하면 최대 순간 저장량을 사전 점검한 뒤 기존 v1 준비 절차를 실행한다. 실제 계획 hash와 실제 준비 비용을 예측과 다시 비교한다. 다르면 원본을 보존하고 중단한다.
- 호출자는 반환한 결과/anchor를 capture 밖에 보관하고, 기존 `retire_raw` 및 `replay_retired_capture`를 실행한다. **새 심사 API 자체는 삭제하지 않는다.** 감독기/실시간 수집의 기본 경로에도 아직 연결하지 않았다.

예측식은 다음과 같다.

`최종 capture 바이트 = 종료 시 capture 바이트 - 삭제 대상 원본 + 계획 + 의도/완료 영수증 + gzip 전용 재생 기록 2회`

재생 2회는 준비 전 검증 1회와 전환 후 검증 1회다. 체크포인트 최종 상태, proof와 영수증을 실제 인코더로 산출한다. 무작위 UUID/해시는 고정 길이이므로 정확히 계산할 수 있다. gzip과 기존 기록은 그대로 남아 종료 시 크기에 이미 포함된다. 심사 예측과 저장된 실제 계획도 비교하므로, 고정된 v1 형식과 계산기의 차이가 생기면 삭제 단계의 anchor를 반환하지 않는다.

최대 순간 추가 공간은 모든 최종 메타데이터와 가장 큰 체크포인트 2개가 원본 삭제 전에 공존한다고 보수적으로 계산한다. 기존 aggregate logical cap과 물리 여유 공간 검사도 유지한다. 실제 물리 디스크 회수량, 메모리 사용량, 무한한 장애 재시도 공간의 상한은 아니다.

큰 입력은 채널별 `per_tick=200`, 주기 100ms, 대기열 1,024, 호가 양쪽 각각 1,000개다. fixture 생산자·수신자 실행 시각은 실시간 스케줄링에 영향을 받는다. 이 표는 해당 실행의 관측이며, 반복 실행마다 같은 바이트 수나 같은 지연을 보장하지 않는다. 0.5초가 최적 설정이라는 결론도 아니다.

첫 matrix 실행도 큰 입력/0.1초에서 `PIPELINE_UNIT_BACKLOG_LIMIT`, `AUDIT_SET_INCOMPLETE`로 중단됐다. 초기 harness는 이 실패를 보고 전체 matrix 실행을 멈추었으므로, 실패를 보존하고 나머지 사례를 계속 기록하도록 harness를 수정했다. 입력률·대기열/작업 한도는 올리지 않았다. [초기 로그](../../reports/validation/retirement_admission_20260918/fixtures.log)와 자료를 별도로 보존했다. 최종 matrix의 `passed`는 거부/보존 동작의 검증이며 이 부하의 수집 성공을 뜻하지 않는다.

## 검증 범위와 제약

- 신규 17개 검사: 손해인 전환의 무기록 거부, 반복 심사의 무증가, 실제 바이트 일치, 경계 1바이트 차이, 사전 정책/anchor/압축 손상/활성 writer·worker/미확정 tail/누락 잠금/기존 준비 흔적 거부, 순간 저장 여유 부족, 계획·저장량 불일치 시 원본 보존.
- 관련 기존 936개와 합쳐 고유 953개를 검증한다. 초기 테스트의 잘못된 파일 이름 부분 문자열 count는 실제 원본 경로 목록 비교로 수정했고 초기 실패 로그·소스도 보존했다. 최종 결과는 위 검증 기록을 따른다.
- 동작/내용을 추가하지 않는 사전 심사다. 삭제·중단 복구 프로토콜은 고정된 v1 그대로이며 이번 단계에서 새로운 SIGKILL 인증을 주장하지 않는다.
- 정상 경로의 **capture 내부 모든 일반 파일 논리 바이트**가 예측 범위다. capture 밖의 연구 보고서/외부 anchor 파일, 파일시스템 할당·스냅샷, 추가 재생, 중단 후 남긴 임시 파일은 이 순절감 수치에 포함하지 않는다. 장애 흔적은 삭제하거나 숨기지 않는다.
- 기존 v1의 완료 원장 및 모든 epoch의 clean-stop 요구를 그대로 적용한다. 재연결/중단 자료를 임의로 적격 처리하지 않는다. 기존 `retirement/` 또는 `retirement-replay-*`가 있으면 새 심사를 반복하지 않고 복구 경로로 넘긴다.
- 모든 새 파일은 기존 run budget에 속한다. 저장 공간 검사는 예비 공간을 독점 예약하지 않으므로 다른 프로세스가 디스크를 사용하면 이후 저장이 거부될 수 있다. cooperative single-owner 계약과 기존 fail-closed 동작을 유지한다.

## 다음 순서

1. **압축 전환 상태를 감독기 복구에 연결.** raw를 필요로 하는 옛 복구 함수에 전환된 capture를 넘기지 않게 구분하고, 외부 anchor로 고정된 계획의 gzip 경로를 사용한다. 과거 형식/소스 binding을 완화하지 않는다.
2. **수집 중 확정 구간의 전환을 새 계약으로 구현.** 활성 journal의 기존 체크포인트는 모든 원본을 참조하므로, 현재 종료 자료 API를 수신 callback에 붙이는 것으로 해결되지 않는다. 원본/압축 위치의 고정 목록과 인계·삭제·재생 위치의 순서를 설계하고 중단 시험한다.
3. **유한 원장/체크포인트 회전과 통합 부하 확인.** 압축된 최종 크기, 전환 전 최대 공간, 대기열 처리 속도를 함께 확인한다. 0.1초 부하 실패를 무시하거나 한도를 늘려 통과시키지 않는다. 그 뒤 짧은 공개 확인과 더 긴 기술 시험 등록을 판단한다.
