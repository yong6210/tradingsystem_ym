# 유한 구간 회전 수집과 전환 공백 v1

2026-09-18. 기존 [수집 중 보관 전환](RETAINED_FEED_COLLECTOR_V1.md)의 원본/gzip 복구 계약은 유지하고, **한 pipeline의 원장과 체크포인트가 실행 전체를 계속 떠안는 구조**를 분리한다. 이전 코드·검증 자료는 변경하지 않는다.

## 구현 범위

[새 실행기](../../app/research/data/rolling_retained_capture.py)는 하나의 저장 소유자와 최초 시간 창 아래 `shard-00`, `shard-01` 등의 독립 namespace를 생성한다. 각 구간은 기존 RetainedFeedPipeline/RetainedFeedEpoch를 사용한다. 정해진 구간 종료 시각에 STOP을 기록하고, 소켓 종료·감사/압축/보관 전환·작업자 회수를 완료한 뒤 결과 hash를 상위 원장에 저장한다. 다음 구간은 작업 번호0·새 journal/체크포인트/processor·새 연결/REST snapshot부터 시작한다.

[전환 제어기](../../app/research/data/rolling_feed_epoch.py)는 실제 수집 종료 시각만 별도로 받는다. RUN_WINDOW와 감사 계약의 시작/끝은 최초 전체 창 그대로다. 중간 종료는 `PLANNED_ROLLOVER`, 마지막 종료는 `ORIGINAL_DEADLINE`으로 구분하며, 수신 프레임을 간추리거나 버리지 않는다. 압축용 봉인 주기와 시세 수신 주기를 혼동하지 않는다.

[상위 기록](../../app/research/data/rolling_capture_log.py)은 `INIT → BEGIN → READY → END … → FINISH` hash chain이다. READY는 두 작업/보관 원장의 초기 anchor를 저장하며 **epoch 생성·네트워크 요청보다 먼저** 확정한다. END는 완료 결과 파일의 이름과 hash를 고정한다. 완료된 구간의 내용은 덮어쓰거나 삭제하지 않는다. 해당 구간에서 이미 허용된 합성 원본→gzip 전환은 기존 계약대로다.

이것은 journal 파일 번호만0으로 되돌리거나 감사 history를 없애는 방식이 아니다. **구간별 active metadata를 새 namespace로 넘기는 유한 회전**이며, 전체 디스크 파일 목록·원본/gzip·종료 결과는 계속 누적된다. 외부 보고서와 fixture 참조본을 제외한 실제 capture의 모든 파일은 같은 저장 예산에 들어간다.

## 사전 한도

- 전체 창은 여전히 최대120초, 최대16구간이다. 24시간 등록/daemon은 없다.
- 구간 길이1~30초, 기본10초. 봉인 주기0.5~2초, 기본0.5초. 이전에 대기열이 넘친0.1초 설정은 이 새 qualification runner에서 사전 거부한다. 기존 runner의 한도와 실패 기록은 유지한다.
- 사전 작업 수 상한은 `ceil(min(전체 창, 구간 길이)/봉인 주기)+2`다. 마지막 봉인과 경계 여유를 포함해 기존 구간당62작업 한도를 넘는 설정을 거부한다. 최대 pending4·예약2·작업자15초·동기500ms 한도는 늘리지 않는다.
- 상위 원장은 최대50이벤트/이벤트128KiB/총4MiB, 구간 결과 파일은 최대8MiB다. 구간 수를 줄였다 늘리며 성능 결과에 맞춘 탐색은 하지 않는다.
- 초기 총 구간 수/작업 수 심사는 시간·개수 계약이다. 전체 디스크 바이트를 장기간 예측하는 성능 보증과는 다르다. 실제 쓰기마다 전체 파일 예산과 물리 여유를 검사한다.

0.5초 이상이라는 입력 조건은 모든 시장/장비에서 통과한다는 보증이 아니다. 입력량이 처리 속도를 넘으면 기존 실패 경로로 중단한다. 시장 신호/매매 파라미터 튜닝도 아니다.

## 복구와 실패 처리

capture 밖에 `{storage, rolling_anchor}`를 보존한다. resume는 같은 부팅·단조시계/벽시계·코드 hash·저장 계약·원장 chain을 확인한다. 완료 결과는 hash 확인뿐 아니라 해당 raw/gzip custody와 revision0의 cold replay, 저장 감사 상태의17개 의미 항목까지 대조하고 나서 다음 네트워크 요청을 허용한다.

- READY 전 중단: 새 epoch/네트워크가 없었음을 확인하고 자료를 보존한다.
- READY 후 미완료 구간: 그 구간에 영속 인계된 작업을 혼합 소스로 복구하고 이번 시험 창은 `PROCESS_INTERRUPTED`로 끝낸다. 새 실시간 연결로 조용히 대체하지 않는다.
- END 파일만 있고 이벤트가 없는 경우: orphan 결과를 보존하고 인계 작업에서 복구한다. orphan 결과를 완료 증거로 채택하지 않는다.
- END 이벤트가 저장된 경우: 완료 구간을 검증한다. 원래 종료 시각이 남았다면 명시적 `run()` 호출로 다음 구간을 시작할 수 있고, 지났다면 연결0으로 종료한다.
- 원장 rollback/파일 손상/미등록 custody는 기존과 같이 거부한다. 완료 후 반복 resume/run은 파일 내용 변경·추가와 새 연결이 없어야 한다.

이번 runner는 전송 장애 시 재시도 없이 창을 종료한다. 기존 감독기의 retry 예산을 구간마다 새로 주는 우회는 하지 않는다. **상시 재시작·동일 연결을 유지하는 무중단 회전·이전 감독기와의 완전한 결합은 아니다.**

## 검증 계약과 결과 위치

[검증 기록](../../reports/validation/rolling_capture_20260918/verification.json), [신규 테스트](../../tests/test_rolling_retained_capture.py), [고정 훈련 스크립트](../../scripts/verify_rolling_retained_capture.py).

- 신규21개를 포함해 고유1,042개 검사(연구424/실행618)를 수행한다. 계획 거부, 개수 한도, cold replay17항목, 공백 제외, 종료/재개, 총 저장량, 손상과 중단 경계를 포함한다.
- 고정40초 합성 수집: 구간8초·봉인0.5초·한쪽1,000호가·공개 입력100ms당20개. 별도 market producer를 사용한다. **총작업 수62초과**, 구간별18작업 이하, 이전 구간 파일 불변, 전체 시간 창/공백 유지가 통과 조건이다.
- READY rename 뒤, 원본 unlink 뒤, 결과 저장/END 전, END rename 뒤, 두 번째 BEGIN rename 뒤, FINISH rename 뒤의 실제 SIGKILL6곳. 다른 프로세스에서 최초 종료 시각 이후 복구하고 재복구한다. 복구 시 연결0·기존 증거 보존·전체 시간 창 유지가 통과 조건이다.
- gzip, 남은 raw JSONL, 결과 JSON, 나머지 metadata/임시 파일을 겹치지 않게 합산해 **저장 예산의 사용량과 모든 파일의 실제 바이트 합**을 대조한다. 삭제량에서 일부 metadata만 뺀 값을 전체 절감액으로 표현하지 않는다. 미래 입력률에 대한 용량 예측은 하지 않는다.

최종 실제 작업 수, gap 길이, 크기와 성공 여부는 검증 JSON과 하위 `qualified/capacity` 자료를 따른다. 초기 실행도 보존한다. 검사 개수는 전략 수익성이나 전체 프로젝트 완료율이 아니다.

## 이 접근의 한계와 다음 판단

구간 전환 때 연결을 닫고 drain한 뒤 새 snapshot을 받으므로 전환 비용이 관측 공백으로 생긴다. `combine_epochs`가 이 공백을 메우지 않는지 검사한다. **구간별 기록 한도를 해결했다고 자료 품질99.5%를 충족했다고 볼 수 없다.** 짧은 구간을 계속 반복하는 방식은 장기 표본의 적격 비율을 떨어뜨릴 수 있다.

다음 판단은 전환 공백과 총 저장 비용의 측정 결과를 기준으로 한다. 무중단 연결/검증된 상태 인계 구조가 필요할지, 긴 구간에서도 기존 한도를 지킬 수 있을지 먼저 정한다. 이를 확인한 뒤 새 경로의 짧은 공개 확인과 장기 기술 시험 등록을 검토한다. 현재 전체120초 한도, 실제 새 공개 관측0, 실주문0, 전략 미채택을 유지한다. 미완료 구간의 자동 재시작이나24시간 운용을 이번 결과로 인증하지 않는다.

## 이번 측정에 따른 채택 판단

[판단 기록](../../reports/validation/rolling_capture_20260918/decision.json): **재연결 기반 회전을 장기 수집 기본안으로 채택하지 않는다.** 고정40초 시험의 총76작업은5개 구간, 구간당 최대16작업으로 처리됐다. 종료된 구간 내용과17개 재생 항목은 일치했으나, 전환4회 사이의 기록상 공백 합계는2.155484초(5.38871%)다. 다른 모든 공백을 무시해도 적격 비율 상한94.61129%로99.5% 목표에 못 미친다. 상위 디렉터리 포함 전체 실제 파일은5,487,450바이트였으며, 이는40초 합성 입력의 측정값일 뿐 하루 용량 예측이 아니다.

이 판단 때문에 구간 길이나 봉인 주기를 계속 바꿔 통과하는 숫자를 찾지 않는다. 이번 코드는 유한 회전·복구 경계를 검증한 비교용 실행기로 남기며 기존 수집 경로를 대체하지 않는다. 상시 수집 문제를 해결했다는 결론도 내리지 않는다.

## 다음 구현의 경계 — 같은 연결에서 기록 세대만 인계

다음은 아직 구현/검증되지 않은 설계다. 구현을 시작할 때 별도 버전과 검증 증거를 만든다.

1. **연결과 저장 세대를 분리한다.** 정상 회전에서는 WS/REST session과 MarketFeedProcessor를 유지한다. 단지 파일·작업 원장·감사 체크포인트의 저장 세대만 전환한다. 프로세스 자체가 죽은 경우에는 이 규칙을 적용하지 않고, 기존처럼 공백·새 snapshot을 요구한다.
2. **정확한 경계를 먼저 확정한다.** 원본 순번 N까지의 저장 영수증, 마지막 원본 hash, 감사가 처리한 순번/영수증, 전체 시간 창·시계·processor epoch·session 식별자, 다음 세대 식별자를 인계 문서로 고정한다. 시작점0으로 되돌려 중복/누락을 감추지 않고 전역 N→N+1을 확인한다.
3. **상태의 근거를 연결한다.** 다음 감사 세대의 시작 상태는 이전 인계 순번에서만 만들며 상태 hash뿐 아니라 그 상태를 만든 원본 prefix/감사 계약에 묶는다. 임의 snapshot이나 새 RUN_WINDOW를 만들어 기존 세션을 재현한 척하지 않는다. 기존 raw-only v1 reader가 새 continuation을 모르게 허용하는 변경도 하지 않는다.
4. **인계는 확인 후 전진한다.** 다음 세대의 준비 기록을 먼저 fsync하고 확정 영수증 뒤에만 새 기록을 공개한다. 양쪽 영수증/rename/ACK 유실 때 어느 세대가 N+1을 소유하는지 한 곳에서 판정한다. 미확정 자료와 임시 파일은 보존한다. 수신 대기열은 유한하며 가득 차면 중단하지, 무제한 메모리 버퍼나 조용한 프레임 폐기로 우회하지 않는다.
5. **이전 작업은 제한된 수만 남긴다.** 이전 세대의 압축·감사는 명시한 source ticket만 읽게 하고, AUDIT/custody 완료 뒤에만 원본을 전환한다. 과거 세대 전체를 매 구간마다 메모리로 읽거나 재검증하지 않도록 manifest/index 회전도 별도 한도로 묶는다. 총 디스크 예산에는 모든 세대의 결과/원장/임시 파일이 포함된다.
6. **종료 조건을 먼저 둔다.** 같은 부하에서62개를 넘는 작업, 회전 중 WS 재연결0·추가 REST snapshot0, 입력 순서/건수 보존, 원본 전체 재생과17개 의미 항목 일치, 전역 순번 중복/누락 거부, 인계 강제 종료/재복구, 예약·메모리·총 저장량 상한을 확인한다. ‘연결을 유지한다’는 이유만으로 공백0을 선언하지 않고 watchdog/자료 만료와 원래 달력 분모로 계산한다. 이 증거 전에는 공개 장기 수집/24시간 등록을 진행하지 않는다.
