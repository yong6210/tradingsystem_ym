# 코드 구조와 계약

## 책임 분리

다음은 목표 구조다. **현재 구현은 `foundation/`, `data/minutes.py`, `diagnostics/entry_information.py`**다. 특징·신호는 동결된 기존 함수를 어댑터로 사용하며 별도 규칙으로 대조했다. 나머지는 해당 단계에서 만든다.

```text
app/research/
  foundation/      실험 명세·단위·시간 창·검사. 주문이나 수익 계산 없음
  data/            [예정] 원본 읽기·해시·정규화·연속성·완료 봉
  features/        [예정] 과거 정보에서 특징 계산, 가용 시각 명시
  signals/         [예정] 진입/청산 의도. 계좌·주문 상태 수정 금지
  diagnostics/    [예정] 고정 기간 가격 결과·대조군·분포·의존성
  execution/      [예정] 주문 생명주기·거절·체결·비용·대기열 가정
  accounting/     [예정] 체결/펀딩 이벤트로 잔액·수량·평가 재구성
  risk/           [예정] 수량·손실·총/순노출 제한. 체결을 만들어내지 않음
  portfolio/      [예정] 예산·신호 우선순위·상계. 각 전략 신호 수정 금지
  experiments/    [예정] 단계 실행·재현·등록·중단 기록
configs/research/  검토 가능한 명세; 결과에 맞춰 자동 변경 금지
scripts/          인자 처리와 위 모듈 호출만; 전략 로직·기간별 복제 금지
reports/          불변 실행 결과와 사람이 읽는 보고서
```

실험의 의존 방향은 `자료 → 특징 → 신호 → 진단`이다. 매매 엔진 단계에서는 `신호 → 위험 제한 → 주문 → 체결 → 원장 → 측정` 순서로 분리한다. 보고서는 저장된 측정 결과만 읽으며 재계산·후보 선택을 하지 않는다. 연구 모듈은 거래소 주문 클라이언트를 import하지 않는다.

## 핵심 계약

| 대상 | 필수 정보와 규칙 |
|---|---|
| 자료 | 원본 경로·해시·종목·시장 종류·UTC·시간 단위·품질 상태·가용 기간 |
| 특징 | 대상 시점·사용한 마지막 원본 시점·실제 가용 시점. 현재 봉의 미완료 고저가 금지 |
| 신호 | 고유 ID·모델 버전·방향·판단 시각·사용 정보 시각·판단 이유. 수량이나 체결은 포함하지 않음 |
| 주문 | 신호 ID·제출·활성·만료 시각·수량·가격·주문 종류·reduce-only·상태 |
| 체결 | 주문 ID·체결 시각·수량·가격·메이커/테이커·수수료·체결 근거 |
| 원장 | 모든 수량/잔액 변화가 체결·수수료·펀딩 이벤트로 설명됨. 보고서 숫자로 역산해 메우지 않음 |
| 실험 | 질문·자료/소스 해시·기간·가정·주 지표·실행 상태·코드 버전·실패 기록 |

시간은 timezone-aware UTC를 사용한다. 기간은 `[start, end)`로 통일한다. 미래 가격은 결과 평가 모듈에만 전달한다. 첫 진단에서는 `특징 가용 ≤ 판단 < 평가 진입`을 만족시키도록 판단 뒤 1분 지연을 명시한다. 이 값은 실제 거래소 지연 추정이 아닌, 같은 시점 체결의 낙관성을 피하는 진단 규칙이다. 기존 엔진과 다르므로 별도 버전으로 관리한다.

돈·수량·가격·bp·비율·분 단위를 이름과 타입에 명시한다. `return_pct`와 `return_fraction`을 섞지 않는다. 신호 없음, 자료 없음, 체결 실패, 거래 불허를 같은 0으로 덮지 않는다. 검증은 `assert`에만 의존하지 않고 명시적인 예외를 사용한다.

## 주문과 원장 단계에서 반드시 구현할 것

주문 상태는 제출 → 활성 → 부분체결/체결 또는 취소/만료/거절로 구분한다. 추가 매수와 익절 주문의 슬롯은 분리하되 공유 재고·위험·거래량을 제한한다. 봉 내 사건 순서가 불명확하면 정책과 결과 범위를 공개한다. 진입 직후 같은 봉의 유리한 반등을 가정하지 않는다. 손절·시장가·펀딩은 메이커 무료 가정과 별개로 기록한다.

롱/숏·부분체결·갭·평균단가·잔여 재고·전량 청산·마감 청산을 작은 손계산 사례로 검증한다. 원장은 별도 검산 코드로 재구성한다. 위험 한도는 주문 승인 시점 조건과 실제 최대 손실 보장을 구분한다.

## 가독성과 변경 규칙

- 한 함수는 하나의 책임을 갖는다. 한 줄에 여러 대입·조건·호출을 이어 쓰지 않는다.
- 공개 함수에는 입력/반환 타입과 단위·시간 의미를 쓴다. 반복 숫자는 이름 있는 명세에서 가져온다.
- 파라미터는 JSON 명세에, 규칙은 작은 함수에, 입력/출력은 어댑터에 둔다.
- 설정의 모르는 키·잘못된 타입·NaN·중복 지표·잘못된 기간은 즉시 오류 처리한다.
- 성능 개선은 측정 후 수행하며 가독성을 해치는 배열 최적화에는 기준 구현과 동등성 테스트가 필요하다.
- 기능 변경, 버그 수정, 수익성 실험, 단순 정리는 기록에서 구분한다.
- 테스트는 구현을 그대로 복사하지 않고 반례·손계산·불변식으로 구성한다.

## 기존 코드의 처리

| 기존 부분 | 처리 |
|---|---|
| `multistrategy.py`, `multistrategy_audit.py`, `recycling_portfolio.py` | 역사적 실험 엔진. 소스 해시를 유지하며 당장 이동·대규모 정리하지 않음 |
| `scenario_inventory.py` | 손계산 사례와 원장 계약을 검토해 차후 재사용/이관. 검증 없이 새 엔진의 정답으로 삼지 않음 |
| ZIP 품질 검사·manifest | 검증된 자료 계약 재사용. 공통 로더는 새 단계에서 만들고 이전 입력과 비교 |
| 기간별 복제 runner | 과거 재현용 보존. 신규 실험에는 기간을 인자로 받는 하나의 runner 사용 |
| 보고서 앱 | 저장된 결과를 표시하는 역할만 유지. E001 실행 전 성과 칸을 새 숫자로 채우지 않음 |
| 운영 서비스·거래소 연결 | 이번 기획/진단의 수정 범위 밖 |

완료의 정의는 “코드가 실행된다”가 아니라 **명세 일치 + 의미 있는 테스트 + 독립 검산 + 재현 방법 + 한계 기록**이다. 지금의 설계 검사 통과는 이 중 명세 구조·참조 일관성에만 해당한다.
