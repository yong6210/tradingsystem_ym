# 활성 기록기의 원본·압축본 위치 추적과 복구 v1

2026-09-18. 이전 [압축 보관 인식 감독기](RETENTION_FEED_CAPTURE_V1.md)는 **종료된 capture**만 전환했다. 이번에는 다음 파일을 쓰는 기록기가 앞서 닫은 확정 구간을 전환하고 계속 기록할 수 있도록 `RetainedSealedJournal`을 추가했다. 기존 기록기·자료는 수정하지 않았다.

**이번 완료 범위는 기록기 부품이다. 실제 시장 수집기, 감사 원장, 감독기의 중단 작업 복구에는 아직 연결하지 않았다.** 시장 자료의 장기 수집이나 수익성 검증을 완료한 것이 아니다.

## 확인한 원인과 변경

기존 기록기는 다음 commit에서 변경된 파일만 fsync하므로 과거 원본이 없어도 진행할 수 있었다. 그러나 재개는 모든 원본 파일을 읽는 검증 함수를 사용해 압축 전환 후 실패했다. 또한 다음 파일 번호를 디스크에 남은 원본 이름만으로 계산하면, 최신 원본이 모두 삭제됐을 때 이전 번호를 재사용할 수 있었다.

새 기록기는 다음을 명시적으로 관리한다.

- 생성 시 고정한 보관 정책 및 구현 hash. 과거 기록기에 소급 적용하지 않는다.
- 구간별 확정 ticket, 등록 gzip 위치, 압축 descriptor hash, 이전 입력 cursor.
- capture 밖 호출자가 보관할 handle의 구간 등록 hash와 체크포인트 순번/hash.
- 원본 삭제 의도와 완료 기록. 등록만으로 사라진 원본을 정당화하지 않는다.
- 다음 파일 번호는 디스크에 남은 원본뿐 아니라 체크포인트에 기록된 모든 구간을 고려한다. 미확정 고아 파일도 덮어쓰지 않는다.

## 실행 순서

1. 기존 seal/fsync 프로토콜로 구간을 확정한다. 현재 쓰는 파일이나 변경 중인 파일은 전환 대상이 아니다.
2. 기존 별도 압축 작업자가 gzip을 등록한다. `admit_archive(ticket, ref)`가 원본 전체 바이트와 압축 복원 결과를 비교하고 seal/descriptor를 확인한다.
3. 구간 등록 및 의도/완료 기록을 더했을 때 최소 순절감 조건을 만족하면 등록한다. 작은 구간은 파일 변경 없이 거부한다. **등록 호출은 원본을 삭제하지 않는다.** 새 handle을 별도로 저장한다.
4. `finish_retirement(names=[...])`로 준비된 대상만 전환한다. 대상 전체의 검증이 끝난 뒤 의도 저장→원본 unlink→디렉터리 fsync→완료 저장 순서로 진행한다. 압축본은 그대로 남는다.
5. 이후 다른 파일의 append/commit/seal을 계속한다. 전환 당시 다음 파일이 열려 있고 이미 commit된 상태도 시험했다.
6. 재개 시 외부 handle에 고정한 목록으로 원본 또는 gzip을 명시적으로 선택해 전체 확정 prefix를 검증한다. gzip 검증 실패를 원본으로 우회하지 않는다. 저장된 체크포인트 anchor가 현재 record chain에 포함되는지도 확인한다.
7. 검증 후, commit은 됐지만 seal이 없던 원본 꼬리 구간에 한해 seal을 재발행하고 새 writer epoch를 시작한다. 시장 processor/order book의 복원이 아니다.

## 비용과 유한 범위

- 한 전환 호출은 **명시한 최대 16개 대상**만 검사/처리한다. 등록이 16개 이하면 대상을 생략해 전체를 처리할 수 있다. 과거 모든 gzip을 매 구간마다 다시 검사하는 사용을 피하도록 API를 구분했다. 재개 시의 전체 검증은 유지한다.
- 삭제 시 미결 작업자 예약이 있으면 거부한다. 호출자는 대상 원본을 사용하는 소비자가 모두 끝났음을 보장해야 한다. 별도 소비자별 lease나 시장 감사 완료 조정은 아직 제공하지 않는다.
- 구간 최대 8MiB, journal 최대 1,024개 구간, 등록 문서 최대 32KiB, 등록 디렉터리 항목 수 제한 및 기존 공용 저장 예산을 유지한다. 파일 수/체크포인트가 시간에 따라 늘어나는 구조의 **회전 구현은 아직 없다.**
- 정상 경로 절감량은 이미 원본+gzip이 존재하는 상태에서 원본을 없애고 등록·의도·완료 파일을 더한 차이다. gzip 생성 비용을 없다고 계산한 전체 압축률이 아니다. 외부 연구 보고서/handle 저장 비용과 장애 임시 파일은 정상 경로 예측 밖이다. 임시 파일은 실제 공용 예산에는 포함한다.
- 부모의 검증/fsync는 동기 처리다. 16개 제한이 지연시간 보장은 아니며, 실제 입력/감사/저장 동시 부하 시험이 필요하다.

## 검증 결과

[최종 강제 종료 계획](../../reports/validation/retained_journal_20260918/drills_final/plan.json), [4개 사례](../../reports/validation/retained_journal_20260918/drills_final/summary.json), [종합 검증](../../reports/validation/retained_journal_20260918/verification.json).

새 합성 record 1을 확정·압축·등록하고, record 2의 파일을 **열린 상태로 commit한 뒤** 첫 원본의 전환 도중 부모를 실제 SIGKILL했다.

| 중단 지점 | 확인한 재개 동작 |
|---|---|
| 의도 임시 파일 fsync 뒤 | 임시 파일 보존, 원본/gzip 상태 검증 후 전환 완료 |
| 원본 unlink 뒤 | 등록+의도로 원본 부재 확인, 복원용 원본 파일을 생성하지 않고 완료 |
| 원본 디렉터리 fsync 뒤 | gzip과 남은 원본의 연속 record chain 검증 |
| 완료 임시 파일 fsync 뒤 | 임시 파일 보존, 완료 기록 확정 |

4개 모두 압축 record 1 + 원본 record 2를 정확히 읽고, 재개 후 record 3을 새 epoch·파일 번호 2로 기록했다. 다시 재개해서 순번 `[1,2,3]`, 원래 prefix hash 보존, 소스 `[GZIP,RAW,RAW]`를 확인했다. 전환 반복 및 추가 쓰기 없는 재개에서는 파일 증가가 없었다. 새 append에 따른 journal checkpoint 변경은 정상 변경으로 별도 계산했다.

신규 24개 검사는 혼합 재생, 모든 원본 전환 뒤 번호 재사용 방지, 정상 경로 비용 일치, 작은 구간 거부, 미결 작업자 차단, gzip 손상/의도 없는 유실/원본 재등장/오래된 handle/체크포인트 rollback 거부, 미확정 꼬리 보존, commit된 미봉인 구간 복구, 고아 파일 보존, 대상 배치 제한 등을 포함한다. 기존 971개와 합쳐 고유 995개를 검증한다. 최종 통과 여부는 종합 검증 기록을 따른다.

초기 22개 개발 검사와 초기 SIGKILL4개도 통과했으나, 이후 자체 검토에서 대상 배치 제한을 추가했다. 초기 소스·로그·자료는 보존했으며 최종 숫자에는 중복 합산하지 않는다.

## 거부·한계와 다음 작업

- 등록 파일이 있는데 외부 handle에 해당 hash가 없으면 자동 채택하지 않는다. 최신 외부 영수증 저장 서비스는 별도다.
- 확정 원본에 미확정 suffix가 붙었거나 checkpoint 임시 파일이 남은 경우 자동으로 잘라내지 않고 점검을 요구한다. 모든 임의 중단 지점의 무인 복구 인증이 아니다.
- 압축본이 손상됐으면 원본이 남아 있어도 조용히 우회하지 않는다. 잘못된 자료로 계속 진행하는 것을 막는다.
- 이 부품의 일반 record 재개와 시장 자료의 epoch/감사 재개는 다르다. 실제 collector는 새 연결·스냅샷·시장 상태를 유지하는 기존 원칙과 함께 통합해야 한다.
- 이전 큰 입력/0.1초 구간 대기열 초과는 아직 미해결이다. 24시간 미등록, 시장 수집 창 최대 120초, 신규 전략 미채택을 유지한다.

다음은 **압축/감사 작업 완료와 이 구간 전환을 조정기에 연결하고, 중단 작업 복구도 혼합 소스 목록을 사용하도록 통합**하는 것이다. 이후 유한 원장/체크포인트 회전, 동시 부하, 짧은 공개 확인, 더 긴 기술 시험 등록을 진행한다. 단위 부품 검증을 실제 장기 수집 성공으로 확대하지 않는다.
