# 수집 중 구간 압축·증분 감사 통합 v1

2026-09-18. **실제 수집기 코드 경로에 통합하고 오프라인 전송·부하 시험을 통과했다. 이번에는 Binance에 접속하지 않았다.**

[앞 단계](BACKGROUND_INCREMENTAL_AUDIT_V1.md)의 압축/감사 작업자를 수집 중에 호출하는 v6 수집기를 만들었다. 부모가 하나의 저장 예산과 예약 배정을 관리한다. 확정한 원본·감사 구간의 압축 등록을 확인한 뒤 gzip을 재생하며, 원래 관찰 창과 재연결 전 epoch의 검증 책임을 유지한다. 이전 수집기와 검증 자료는 수정하지 않았다.

근거: [검증 기록](../../reports/validation/pipelined_feed_collector_20260918/verification.json), [고정 부하 계획](../../reports/validation/pipelined_feed_collector_20260918/drill/plan.json), [8개 사례 결과](../../reports/validation/pipelined_feed_collector_20260918/drill/summary.json).

## 수집 경로

1. `PipelinedFeedEpoch`가 원본과 관찰 감사 기록을 기존 fsync/순번 규칙으로 저장한다. 두 기록기 모두 `SealedJournal`을 사용한다. 원본 회전은 정책의 128MiB보다 엄격한 8MiB로 제한하고 실제 값을 plan에 적는다. 감사도 8MiB다.
2. 기본 2초마다, 그리고 epoch 종료 시 마지막 확정 감사 순번과 원본 순번이 같은 경계에서 구간을 닫고 인계한다. 기록 후 아직 감사하지 않은 원본이나 bridge의 미처리 입력이 있으면 인계하지 않는다.
3. `SealedFeedPipeline`이 수집 실행 전체에 걸쳐 공용 예약 2개를 배정한다. raw/audit 압축 감독자와 증분 감사 감독자를 epoch마다 소유하며, 각 감독자에는 실행 중 작업 1개까지만 배정한다. 준비된 감사를 먼저 배정하고, 나머지 공간에는 오래된 미압축 입력을 넣는다.
4. 한 단위의 원본과 감사 구간이 모두 압축 등록돼야 감사를 배정한다. 한 epoch 안에서는 감사 순서를 유지한다. 다음 단위의 압축과 이전 단위의 감사는 동시에 진행할 수 있다.
5. 부모는 증분 감사 결과의 연결·구조를 검사하고 체크포인트를 저장한다. epoch 종료 시 제출된 모든 단위가 완료돼야 최종 raw/audit cursor를 사용해 최종화를 요청한다. 최종화를 완료한 epoch만 전체 품질 결합에 사용한다.
6. 재연결 대기와 새 연결/REST가 진행되는 동안에도 이전 작업자의 실패를 감시한다. 실패하면 수신·연결·REST를 중단하고 성공 품질을 거부한다. 원래 달력 창은 줄이지 않는다.

이번 공통 조정기가 해결한 문제는 **각 작업자의 대기열을 독립적으로 채워 공용 예약 2개를 초과하던 통합 위험**이다. 제출 전 여유를 배정하되 부족한 상태에서 몰래 자료를 버리거나 무한히 대기하지 않는다. 디스크 공간의 실제 예약 검사는 배정 시에도 수행한다.

## 한도와 예외

| 항목 | 계약 |
| --- | --- |
| 수집 기간 | 기존과 동일하게 최대 120초, 24시간 시험 미등록 |
| 구간 인계 | 기본 2초, 종료 시 잔여 구간; 원본 최대 16개+감사 정확히 1개인 단위 |
| 단위 대기 | 실행 포함 최대 4개, 전체 최대 62개; 완료한 단위도 전체 한도에서 제외하지 않음 |
| 단위 시간 | 인계 제출부터 완료까지 최대 15초; 작업자에 아직 배정되지 않은 대기도 포함 |
| epoch | 실행 전체 최대 8개; 재연결로 공통 저장·단위 한도 초기화 금지 |
| 작업자 | 공용 예약 최대 2개; 각 압축/감사 감독자의 기존 64개 작업·15초·RSS 한도 유지 |
| 종료 감사 | epoch 종료부터 최종화까지 15초, 실행 종료 후 drain 15초 |
| 동기 기록 | 기존 500ms 개별/합산 감시 유지, 구간 확정과 flush+seal 합산 지연에도 적용 |
| 입력 과다 | 한 단위의 감사가 여러 segment가 되면 거부; 임의 경계 추정·절삭 금지 |
| 초기 공간 | 최대 크기 작업 2개에 대한 추가 여유를 연결 전에 검사하고, 실제 작업 배정 시 재검사 |

120초가 모든 입력률·재연결 패턴에서 성공한다는 뜻은 아니다. 파일·단위·작업 수나 시간 한도에 먼저 닿으면 실패로 종료한다. 한도 변경이나 장기 가동은 별도 검증이 필요하다.

취소/오류 시 조정기는 자식 작업자를 회수한 뒤 감사 상태 잠금과 run 저장 잠금을 해제한다. 반복 취소가 정리 도중 전달돼도 소유한 정리 작업을 기다리도록 보완했다. 쓰기 실패 뒤 성공 결과를 저장하지 않는다. 전송 오류처럼 저장 자체가 정상인 실패에서는 거부 사유를 담은 진단 결과가 저장될 수 있다.

## 검증 결과

관련 고유 **843개** 검사(기존 813개+신규 30개)를 통과했다. 연구 회귀 424개는 Python 3.12, 실행·부품 검사 419개는 Python 3.14에서 수행했으며 실패·오류·건너뜀은 0이다. 초기 29개 개발 검사에서 예외 종류 기대값 불일치 2건이 있었고 기록을 보존했다. 한도 설정 오류는 `ValueError`, 잘못된 journal/epoch 입력은 `JournalError`로 구분해 정리했다. 정리 중 반복 취소 방어와 조정기의 실제 작업 겹침 검사도 추가했다.

독립 생산자 스레드가 고정 일정으로 입력하고, 유한 큐를 통해 새 수집기로 전달했다. 큰 호가 장부는 bid/ask 각각 1,000개다. 자식 프로세스의 실제 압축·gzip 재생과 부모의 실제 파일/fsync 경로를 사용했다. 각 사례는 별도 프로세스에서 순서대로 실행했고, 실행 중 소스 hash가 변하지 않았음을 확인했다. mock은 전송·의도한 장애·512MiB 시험 저장 한도에 한정했다.

| 고정 사례 | 결과 | 확인 내용 |
| --- | --- | --- |
| 200개/초 설정, 4초 | 예정 종료 | 생성/수신 804개 일치, 단위 8개, 수집 중 감사 완료 |
| 2,000개/초 설정, 4초 | 예정 종료 | 생성/수신 8,004개 일치, 단위 8개, 큐 넘침 없음 |
| 재연결, 4초 | 예정 종료 | 2개 epoch 감사 완료, 생성/수신 604개 일치, 원래 4초 분모 유지 |
| 감사 대기와 다음 압축 겹침, 4초 | 예정 종료 | 공용 예약 2개 안에서 겹침, 생성/수신 804개 일치 |
| 압축 작업자 오류 | 실패 종료 | 수신 중단, 자식 회수, 예약 해제, 품질 거부 |
| 감사 작업자 오류 | 실패 종료 | 수신 중단, 미완료 감사 거부, 자식 회수 |
| 외부 큐 초과 | 실패 종료 | 초과 사실 보존, 생성분을 수신 성공으로 오인하지 않음 |
| 부모 체크포인트 650ms 지연 | 실패 종료 | 생산자는 계속 진행, 지연/상태 오류에서 품질 거부 |

4개 정상 사례의 raw 원본 합계는 10,322개, 관찰 감사는 202개다. 종료 후 독립적인 전체 파일 재생과 각각 **17개 의미 항목**을 비교해 모두 일치했다. 수신 frame은 원본의 `WS`/`CLOSING_WS` 건수와 같고, 생산량은 수신량+종료 시 큐 잔량으로 대조했다. 작업자·생산자 스레드가 모두 회수됐고 공통 예약 잔량은 0이었다.

정상 사례에서 부모 감사 검증/저장 최대 관측은 26.58ms, 부모 압축 검증/등록은 6.13ms, 구간 확정은 4.07ms였다. 최대 관측 자식 RSS는 약 37.66MiB다. 요청 작성 비용을 포함한 전체 event loop 지연 상한은 아니다. 생산자도 Python GIL을 공유하므로 생산 지연을 별도 기록하며, 위 설정을 거래소 입력률 상한이나 장기 처리율 인증으로 사용하지 않는다.

작업 겹침은 동시에 존재한 프로세스를 확인한 것이다. 서로 다른 CPU에서 같은 순간 계산했다는 인증은 아니다. 의도적으로 대기시킨 감사 사례는 배정·수신 지속성 검사이며 전체 처리량 측정으로 사용하지 않는다.

이전 **7,919건** hash 대조(고유 경로 7,650개)가 일치했다. 이전 공개 관측과 실험 결과는 보존했고 이번 부하 자료는 합성 자료로 구분했다. 새 시장 관측 이력은 전진시키지 않았다.

## 아직 완료하지 않은 부분

- **새 경로의 실제 공개 연결 확인:** 이번 전송은 fixture다. 짧은 Binance 공개 수집·의도한 재연결에서 새 경로의 자료·종료·지연을 확인하고 별도 관측 이력을 남겨야 한다.
- **통합 파이프라인의 프로세스 강제 종료와 재개:** 앞 단계는 부품 체크포인트 SIGKILL을 시험했다. 이번에는 실행 중 취소와 자식 오류를 시험했다. 조정기의 단위/최신 외부 영수증은 자동 복구용 영속 원장이 아니며, 전체 부모가 압축/감사 실행 중 사라질 때의 작업자 정리·재구성과 중단 공백 처리는 다음 검증 대상이다.
- **원본 보관 전환과 공간 회수:** 원본과 gzip을 모두 보존한다. 실제로 확보한 공간은 0이며 장기 저장량/파일 수 문제를 해결했다고 보지 않는다. 복구 가능한 압축 등록·감사 상태·소유권 증거를 확인한 뒤에만 삭제 계약을 별도로 설계한다.
- **장기 가동 적격성:** 짧은 합성 부하 통과는 24시간 가동/저장 여유/체결률/거래소 장애 처리 인증이 아니다. 24시간은 여전히 미등록이며 새 전략도 채택하지 않았다.

부모는 시장 재생을 독립 반복하지 않고 고정한 자식 코드를 신뢰한다. 읽기 전용 작업자는 OS 보안 sandbox가 아니다. 동기 fsync는 중간에 강제 중단할 수 없다. 이런 앞 단계의 한계도 그대로 유지한다.

다음 순서: **짧은 공개 수집 경로 확인 → 통합 중단·작업 재구성/복구 → 원본 보관 전환과 장기 저장 한도 → 장시간 기술 시험 등록 판단**. 실제 주문·private 요청·원본 삭제·전략 변경은 없다.
