# 공개 수집 확인·감사 집계 메모리 개선·용량 재측정

2026-09-18. 저장/재생의 기술 검증이다. 새 전략·수익성·체결 확률의 평가가 아니다. [검증 기록](../../reports/validation/feed_scale_20260918/verification.json).

## 이번 결론

분할 저장 경로와 개선된 감사 경로 모두 짧은 실제 Binance 공개 입력에서 확인했다. 감사 관찰을 모두 보관하던 집계를 병합된 구간과 직전 관찰만 보관하도록 개선해, 정상 연속 입력에서 관찰 수에 비례하던 메모리 증가를 줄였다. 구간이 지나치게 분절되면 고정 예산에서 실패 처리하며 정상 구간으로 생략하지 않는다.

24시간 시험은 아직 시작하지 않는다. **장기 원본 전체 재생 비용과 실제 입력량의 변동 상한이 미검증이며, 짧은 관측량의2배 시나리오가 현재 저장 여유를 초과한다.** 이2배는 진단 시나리오이며 검증된 최대 부하나 동결 정책의 새 승인 기준이 아니다.

## 공개 확인

실주문·비공개 API 없이 실행했다. 각 실행은 시작 때 기간과3초 후 의도적 연결 종료를 고정했다. 종료 시각은 재연결로 연장하지 않았고 재연결마다 새 snapshot을 받았다.

[첫12초](../../reports/validation/feed_scale_20260918/public_12s/harness_result.json), [60초](../../reports/validation/feed_scale_20260918/public_60s/harness_result.json), [개선 경로12초](../../reports/validation/feed_scale_20260918/public_compact_12s/harness_result.json).

수집 파일은 전체 저장 예산 안에 있다. 검사기의 계획·수신 확인 상한·측정 결과는 수집 루트 밖의 별도 산출물로, 각 JSON 최대1MiB 제한이다. 이를 수집기의 실패 후 우회 기록으로 사용하지 않는다. 관측 이력은 [새 이력](../../reports/validation/feed_scale_20260918/inspection_history.json)에 이어 붙일 참조로 남겼으며 이전 이력을 대체하지 않았다. 향후 전진 등록에는 이번에 본 자료까지 포함해야 한다.

## 감사 집계 개선과 의미 보존

- [구간 집계기](../../app/research/data/compact_feed_intervals.py): 직전 lease와 이미 병합된 요구사항별 구간·제외 구간을 유지한다. 뒤늦게 처리한 단절의 수신 시각이 과거 구간을 잘라야 하는 경우도 반영한다.
- [감사 재생기](../../app/research/data/compact_feed_audit.py): 기존 확정 원본/감사의 전체 검증, 순번·해시·관찰 대조, 만료·마지막 관찰 이후 추정 금지를 유지한다.
- [수집기 v4](../../app/research/data/compact_feed_collector.py): 기존 저장 epoch와 비동기 제어를 재사용하고 감사기를 교체했다. 기존 동결 파일을 변경하지 않기 위해 버전을 분리했다.
- [검사](../../tests/test_compact_feed_audit.py): 무작위 고정 seed50개, 역방향 제외 구간, 만료, 중복 시각, 고정 시간창, 손상·유실·자원 상한과 실제 수집기 계약을 검사한다.

병합 구간/제외 구간은 전체100,000개, 최종 결과 구간도100,000개 상한이다. 보관량은 관찰 수가 아니라 분절된 구간 수에 영향을 받는다. 상한 도달은 `IntervalLimitError`로 기록하고 적격 구간을 비워 전체 품질을 거부한다. 일부를 잘라서 성공으로 표시하지 않는다. 최종 관찰 한 점만으로 미래 구간을 늘리지 않는다.

[동등성 재생](../../reports/validation/feed_scale_20260918/replay/comparisons.json)에서는 새 공개6개 epoch와 이전 공개 자료를 분할 형식으로 옮긴2개 epoch, 총 **원본13,297개·감사1,349개**를 각각 별도 프로세스로 재생했다. 새 진단 필드를 제외한 모든 결과 필드가 기존 감사기와 일치했다. 기존 자료는 새 표본 수에 중복 집계하지 않았다.

가장 큰 실제 epoch(원본8,160개/감사839개)의 전체 파일 검증·재생은 기존 약0.564초/28.64MiB, 개선 약0.566초/28.13MiB였다. 짧은 파일에서 전체 처리 속도가 개선됐다고 주장하지 않는다. 파일 검증·여러 차례 읽기 비용은 이번 집계 메모리 변경으로 없어지지 않는다.

## 현재 저장 용량

[계산 근거](../../reports/validation/feed_scale_20260918/capacity.json), [재현 스크립트](../../scripts/report_feed_storage_capacity.py).

원본·감사·메타데이터·최종 결과 등 수집 종료 시 남은 모든 정규 파일 크기를 원래 시간창으로 나누어1·2·5배 일정 입력률 시나리오를 계산했다. 단절/초기화도 분모에 남겼다. 보관된 파일 크기이며 체크포인트 반복 쓰기 I/O 총량과 같지 않다.

60초 실행의 최종 보관량7,615,474바이트를 선형 연장하면 하루 **1배10.21GiB,2배20.43GiB,5배51.07GiB**다. 측정 시점의 실제 여유에서16GiB 보존 기준을 뺀 공간은 **15.86GiB**였다. 따라서2배 가정만으로도 약4.56GiB가 부족하다. 구성상64GiB 실행 한도보다 실제 물리 공간이 먼저 제약한다.

다른 두12초의1배 환산도6.33GiB/9.01GiB로 달랐다. 짧은 표본은 입력률 상한·하루 예측·신뢰구간을 제공하지 않는다. 하루 크기로 커지는 manifest, 파일시스템 할당 비용, 순간 쓰기·다른 프로세스 사용량까지 보장한 계산이 아니다. 메모리 개선이 디스크 용량 부족도 해결했다고 해석하지 않는다.

## 검증 상태와 다음 순서

관련 고유 **558개 검사 통과**: 기존 연구424개+실행기96개+새 경로38개. 신규 초기15개와 단독38개 실행은 최종 합계에 중복 가산하지 않았다. 이전 증거1,706건/고유1,437경로 해시 대조 일치. 기존 동결 코드·문서·정책·실험 산출물은 보존했다.

다음은 다음 순서다.

1. 하루 규모의 **전체 원본·감사 파일 재생 비용**을 제한된 합성 자료로 단계적으로 측정한다. 이번 구간 집계만의 성공을 그 근거로 대체하지 않는다.
2. 실제 수집량 변동과 쓰기 비용을 더 관측하고, 필요한 저장 여유·용량 부족 중단·단계적 시험 기간을 정한다. 현재 공간을 충분하다고 승인하지 않는다.
3. 이 근거와 최신 관측 이력, 종료/복구 계측을 묶어 고정24시간 기술 시험 등록 여부를 판단한다. 수익성 전진 평가·실거래 도입은 별도 조건이다.

기존 약9초 지연의 원인은 여전히 미확정이다. 이번에 재현되지 않았다는 이유로 해결 완료라고 기록하지 않는다. 현재 실행기 최대120초 제한,24시간 시험 미시작, 신규 모델 채택 없음, 실주문0을 유지한다.
