# 닫힌 구간의 압축 등록·중단 복구 v1

2026-09-18. 압축률 측정 다음 단계로 공통 저장 예산에 연결되는 `SegmentArchive`를 구현했다. 닫힌 로그 전용 동기 구성요소이며 아직 실시간 수집기에 연결하지 않았다. 원본 삭제/교체는 구현하지 않았고, 기존 사용자 자료와 동결 보고서는 보존했다.

## 등록 계약

대상은 공통 실행 예산 안에 있는, 작성자 잠금을 얻을 수 있는 journal의 확정된 segment다. 기존 검증 뷰가 원본 전체의 순번·hash·checkpoint를 확인한다. 미확정 꼬리나 checkpoint 임시 파일이 있거나 작성자가 열려 있으면 등록을 거부한다. 대상 파일은 최대8MiB, gzip level1, 읽기/쓰기 버퍼64KiB로 제한한다.

등록 순서는 다음과 같다.

1. 원본을 검증하고 run/journal/segment·원본 길이/hash·metadata hash, 순번 범위·끝 record hash·checkpoint hash를 묶는다.
2. 새 임시 압축 파일을 만들며 gzip header/body/trailer까지 공통 예산에 반영한다. 원본·압축본·임시 등록 기록이 동시에 존재하는 양을 모두 계산한다.
3. 압축 파일 fsync 후 전체 압축 hash, gzip CRC, 복원 길이와 원본 hash를 검증한다. 원본이 바뀌지 않았는지도 재확인한다.
4. 압축 파일을 고유 최종 이름으로 rename하고 디렉터리를 fsync한다. 이것만으로는 아직 등록된 자료가 아니다.
5. 전체 내용 checksum이 있는 등록 descriptor를 임시 저장·fsync·rename·디렉터리 fsync한다. 이 descriptor가 등록 기준이다.

descriptor는16KiB, 저장소 파일 수는1,024개로 제한한다. 잘못된 경로/이름/크기/중복 JSON key/등록 정보 checksum/압축 hash/복원 hash를 거부한다. checksum은 우발적인 메타데이터 손상을 검출하는 장치이며 외부 작성자의 악의적 재작성을 인증하는 서명은 아니다. 기존과 같이 단일 소유자·협력적 잠금·같은 로컬 파일시스템을 전제로 한다.

같은 원본의 재등록은 검증된 기존 descriptor를 재사용한다. 이때도 압축 파일·descriptor·디렉터리를 다시 fsync해 중단 뒤 fence를 재확인한다. 미완료 시도 뒤 명시적으로 재시도하면 새로운 파일 이름을 사용하며 이전 임시/미등록 파일을 덮어쓰거나 지우지 않는다.

## 복구와 읽기

복구는 모든 파일과 임시 파일의 용량을 다시 세고 등록된 압축본을 전체 검증·재fsync한다. 압축 파일만 있거나 descriptor 임시 파일만 있으면 자동 등록하지 않는다. descriptor/압축본 손상은 전체 오류로 반환하며 해당 항목을 빼고 성공 처리하지 않는다.

등록된 압축본은 원본의 현재 상태와 별도로 검증할 수 있다. 원본이 없어졌거나 변경됐다면 `MISSING`/`DIFFERS`로 보고하고 `catalog_complete=False`로 표시한다. 원본을 자동 복구/덮어쓰기하지는 않는다. 온전한 압축본의 바이트를 읽어 복구 작업에 사용할 수 있다. 빈 저장소의 catalog 판정은 그 저장소 내부 상태만 뜻하며 전체 journal의 압축 완료 증명이 아니다.

`read_chunks()`는 첫 바이트를 제공하기 전에 전체 압축본과 복원 결과를 검증한다. 허용된 원본 길이보다 확장되면 즉시 거부해 메모리에 무한히 풀지 않는다. 이후 재생 순회에도 길이/hash를 확인한다. 원본을 슬쩍 대신 읽어 손상된 압축본을 정상처럼 처리하지 않는다.

## 시험 결과

- 신규25개 + 기존 연구424개 + 기존 실행/저장218개 = **고유667개 검사 통과**.
- 최종 구현에서8개 저장 지점에 실제 SIGKILL: 압축 chunk 직후, 압축 fsync, 복원 검증, 압축 rename, 디렉터리 fsync, descriptor 임시 fsync, descriptor rename, 마지막 디렉터리 fsync.
- descriptor rename 전6개 지점은 등록0개, 이후2개 지점은 등록1개로 복구됐다. 모든 중간 파일이 그대로 보존되고 공통 용량 계산에 포함됐다. 명시적 재시도 후에는 등록1개와 원본/복원 일치를 확인했다.
- 초기 구현에서도8회 실행했다. 이후 코드 검토에서 descriptor 전체 checksum을 추가하고 최종8회를 반복했다. **총 SIGKILL16회**이며 초기 소스 snapshot과 결과도 별도로 보존했다. 최종 결과는 `drill_hardened`다.
- 기존60초 공개 기록의 복사본에서4개 segment, **원본8,577개+감사898개=9,475개 레코드**를 등록·복원했다. 원본 segment7,596,362bytes → gzip1,116,058bytes였고 모든 원본 바이트/순번 범위/끝 hash가 일치했다.
- 이 복사본의 원본+압축본+metadata를 합친 예산 사용량/최고점은8,718,513bytes였다. 원본을 유지했으므로 확보한 공간은0이다.
- 이전 검증 사슬2,248건/고유1,979경로 해시 대조 일치. 새 공개 요청/관측·실주문0이며 관측 이력은 이전 기록을 이어 쓴다.

SIGKILL은 프로세스 중단 시험이다. 전원 차단, 저장장치 고장, 비협력적 파일 수정의 완전한 보장을 의미하지 않는다. registry 파일이 rename 뒤 보이는 경우 복구 단계에서 다시 검증·fsync한 뒤 사용한다.

## 남은 구현과 순서

1. **수집 중 닫힌 구간의 인계**: 현재 API는 작성자가 닫힌 journal에서만 동작한다.8MiB는 압축 대상 파일 한도이며 원본 전체 검증 시간 한도가 아니다. 작성 중인 journal의 닫힌 segment를 안전하게 넘기는 확정 기록과 별도 작업자 연결이 필요하다.
2. **압축 구간을 사용하는 작은 단위 감사**: 원래 hash 사슬·순번·관찰 시각과 처리 상태를 구간 사이에 이어야 한다. 기존 감사기는 원본 파일을 사용한다. 이번 결과는 압축 bytes의 동등성 검증이며 압축 기반 전체 시장 상태 재생의 실시간 연결 완료가 아니다.
3. **보관 전환/정리와 통합 부하**: 읽기/감사/복구가 압축 구간을 사용한 뒤, 새로 소유한 수집 파일만 대상으로 원본 정리의 중단 복구를 별도 검증한다. 압축 중 이중 공간·대기열·처리 지연도 다시 측정한다. 기존 동결 자료를 지워 공간을 만들지 않는다.

이후 저장 여유를 다시 계산하고24시간 기술 시험 등록 여부를 판단한다. 최대120초 제한·24시간 미등록·전략 미채택은 유지한다. 이번 단계는 전략 수익성을 새로 평가한 작업이 아니다.
