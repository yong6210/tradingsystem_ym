# 원래 수집 창을 유지하는 재시작 감독 v1

2026-09-18. [작업 인계·영수증 복구](DURABLE_SEALED_PIPELINE_V1.md) 다음 단계다. 기존 자료·확정 소스는 보존하고 새 감독기와 공용 저장 예산 뷰를 추가했다. 이번 검증은 합성 전송을 이용한 오프라인 시험이다. 실제 Binance 연결이나 계정 주문은 실행하지 않았다.

## 이번에 연결한 동작

`RestartableFeedCapture.create()`는 최초 수집 시작/종료 시각, 부팅 식별자, monotonic 구현, wall/monotonic 표본, 정책·구현 해시와 저장 한도를 고정한다. `handle()`의 저장 계약과 감독 영수증은 호출자가 보관한다. 프로세스를 다시 실행한 호출자는 이 handle로 `resume()`하고 `run()`을 호출한다.

수집 시도마다 새 디렉터리·원본 journal·시장 processor·연결 세션을 만든다. 이전 체크포인트는 과거 자료 감사에만 사용하며 새 시장 processor로 전달하지 않는다. 새 public/market 연결과 REST 스냅샷을 거쳐야 다시 호가 적격성이 생긴다. 새 시도에도 최초 RUN_WINDOW를 기록한다.

모든 저장과 작업자의 공간 예약은 하나의 루트 소유자와 공용 예산을 쓴다. 시도별 `ScopedFeedBudget`은 경로만 제한한다. 시도가 늘어나도 별도의 공간 allowance나 예약 슬롯을 얻지 않는다. 두 슬롯 상한과 실패 상태를 공유한다.

## 영수증과 재시도

감독 기록은 각 capture 밖의 `receipts/`에 보관한다. INIT → ATTEMPT → 여러 RECEIPT → END → FINISH 순서를 검증한다. 파일은 순번/이전 해시 연결을 가진 불변 이벤트이며, 임시 파일 fsync·원자적 교체·디렉터리 fsync 후 응답한다. 전체4,096개·개별128KiB·합계32MiB 한도와 루트 공간 예산을 함께 적용한다.

각 work-ledger 이벤트의 완료 응답을 감독 RECEIPT로 저장한다. 중간에 종료되면 기존 작업 원장에서 검증한 응답 유실분을 복원할 수 있다. 최초 START 영수증조차 인계되지 않았으면 이전 epoch/네트워크 사용을 인정하지 않고, 남은 파일을 보존한 채 인계 전 중단으로 기록한다. 결과 파일을 저장하고 END를 잃은 경우도 파일을 덮어쓰지 않으며, END에 연결된 새 결과만 집계한다.

ATTEMPT는 연결 또는 대기 전에 기록한다. 두 번째 시도부터 기존1·2·4·8·16·30초 지연을 사용한다. 대기 중 프로세스가 종료돼도 그 시도/재시도는 사용한 것으로 남고, 다음에는 다음 지연을 사용한다. 첫 시도를 포함해 최대7회다. 원래 종료 시각에 도달하거나 다음 대기가 이를 넘으면 새 연결을 하지 않는다. 복구와 감사 정리는 종료 시각 뒤에 끝날 수 있지만 수집 창은 연장하지 않는다.

이 보관은 **같은 로컬 파일시스템에서 capture와 분리한 기록**이다. 원격 백업이나 전원 차단·모든 사본의 동시 후퇴 보호가 아니다. 최신 감독 영수증까지 호출자가 별도로 보관하면 그 이전 후퇴를 검출한다. 최초 handle만 가진 경우 이후 전체 기록의 악의적 동시 후퇴를 검출한다고 주장하지 않는다.

## 시계와 자료 적격성

재개와 각 새 네트워크 요청 전에 부팅 식별자/monotonic 구현을 확인한다. 최초 표본과의 wall/monotonic 차이가 기존100ms 기준을 넘거나 시계가 후퇴하면 거부한다. 표본 획득 불확실성도 검사한다. 이번 실제 프로세스 시험은 macOS의 현재 같은 부팅 환경에서 수행했다. Linux 분기는 구현했지만 별도 실행 검증은 하지 않았다. 재부팅·큰 시계 변경 뒤에는 같은 수집 창의 실시간 재개를 허용하지 않는다.

중단된 구간은 달력 시간 분모에 계속 남는다. 과거 마지막 감사 시점과 새 최초 감사 시점 사이를 연결해 적격 시간을 만들지 않는다. 첫 UNIT 인계 전 중단은 감사 입력0개일 수 있다. 이 경우 빈 prefix를 결과에 보존하고 적격 시간0으로 집계하며, 일반 epoch로 가장하지 않는다.

프로세스 중단이 포함된 결과에는 `PROCESS_INTERRUPTION_OR_UNACKNOWLEDGED_ATTEMPT`로 자료 품질 거부를 남긴다. 복구가 됐다고 완전한 원래 실행으로 승격하지 않는다. 수익성 평가 준비·전략 채택·연속 정상 운용 인증은 모두 미충족 상태다.

## 확인한 증거

[검증 기록](../../reports/validation/restartable_feed_capture_20260918/verification.json), [8개 강제 종료 결과](../../reports/validation/restartable_feed_capture_20260918/drills/summary.json), [재현 하네스](../../scripts/drill_restartable_feed_capture.py).

- 신규22개와 기존886개, 고유908개 관련 검사. 정상 전체 재생, 재연결, 완료 후 재호출, 저장 영수증 유실, 시계/구현 변경, 파일 손상·후퇴, 중복 소유, 취소/예약 해제, namespace 경계, 재시도 한도를 확인한다.
- 실제 SIGKILL8개: 인계 전, 감사 영수증 전, 외부 UNIT 영수증 임시 저장/이름 교체 뒤, 새 epoch의 네트워크 시작 전, 결과 저장 후 END 전, 두 번째 시도의 대기 전, 원래 종료 시각 경과 사례.
- 매 사례는 서로 다른 프로세스에서 최초 실행 → 복구/재개 → 완료 결과 재호출을 수행한다. 새 연결이 가능한6개는 fixture 연결2개·새 스냅샷1개를 수행하고 전체 재생17개 항목과 일치했다. 이미 창이 끝난2개는 새 연결0이다. 세 번째 완료 결과 재호출은8개 모두 연결0이다.
- 재시도 대기에서 중단한 사례는 세 번째 시도까지 총 재시도2회를 사용했다. 중단 전 허가된 재시도를 되돌리지 않았다. 원래 수집 창은0.6·3·4.5초 그대로였고, 중단 시간은 적격 구간으로 연결되지 않았다.
- 기존 파일284개 해시를 유지했다. 필요한 복구에서 과거 replay 체크포인트만 앞으로 이동했으며, 원본·임시 파일·미응답 결과는 삭제하지 않았다. 과거9,315건 해시 대조(고유9,046경로)를 확인한다.

최초 개발 검사22개에서 오류1개/실패1개가 있었다. 실제 오류는 감사 입력0개의 식별자 없는 prefix를 일반 epoch 집계기로 넘긴 것이며, 명시적 빈 prefix 처리/품질 거부로 수정했다. 다른 실패는 프로세스별 공간 최고값까지 재시작 전후 같아야 한다는 테스트 가정이었다. 의미 결과와 현재 사용량을 비교하도록 수정했다. 최초 코드와 실패 로그를 보존했다.

## 아직 남은 것

OS가 프로세스를 자동으로 띄우는 서비스는 설치하지 않았다. 이번 감독기는 명시적으로 재호출하면 과거 작업 복구와 새 세션을 이어가는 API다. 같은 로컬 디스크의 영수증 보관을 원격 보관 서비스로 확대하지 않는다.

짧은 합성 입력 검증은 새 감독 경로의 실제 공개 연결, 큰 장부·버스트 동시 부하, 전원 차단, 장기 용량을 인증하지 않는다. 부모 저장·시계 조회는 동기이며 강제 선점 가능한 지연 상한이 아니다. 전체 이벤트 재검사와 기존 유한 작업 수 상한도 유지한다.
