# 확정 구간의 백그라운드 압축·부모 등록 v1

2026-09-18. 활성 journal이 발급한 seal ticket을 읽기 전용 압축 작업자에게 넘기고, 부모가 저장 공간을 예약해 압축본을 검증·등록하는 부품을 연결했다. **실제 market collector에는 아직 연결하지 않았다.** 기존 journal/seal/archive/collector 모듈과 과거 결과는 변경하지 않고 새 모듈을 추가했다.

## 처리 순서

1. `BackgroundArchives.submit()`이 ticket의 checksum·run/journal/metadata·연속 순번·이전 record/segment/seal hash를 검사한다. 실행 중 작업을 포함한 최대2개 대기열에 넣기 전에 출력 공간을 예약한다.
2. 작업자1개가 구간 하나를 읽고 전체 순번·hash를 검증한 뒤 gzip level1로 압축한다. 저장소에 파일을 쓰지 않으며, 길이가 제한된 표준 출력으로만 반환한다.
3. 부모가 응답의 작업 번호·ticket hash·압축 길이/hash를 검사하고 gzip을 독립적으로 복원해 원본 길이/hash와 대조한다. 자식의 성공 응답만으로 등록하지 않는다.
4. 부모가 자기 예약을 사용해 임시 압축본 저장/fsync → 저장된 압축본 재검증 → 고유 파일명으로 교체/directory fsync → descriptor 원자적 저장/directory fsync를 실행한다. 마지막 확인을 마친 작업만 완료 결과에 넣는다.
5. 실패하면 공통 저장 예산도 실패 상태로 고정하고 다음 작업을 중단한다. `finish()`는 누락이나 실패를 예외로 알리고 자식을 회수한다. 성공한 이전 구간이 있더라도 전체 호출을 성공으로 바꾸지 않는다.

## 저장 공간과 작업 한도

| 항목 | v1 한도/계약 |
|---|---|
| raw segment | 최대8MiB, 기존 seal 계약 |
| 동시에 대기/실행 | 합계2개, 실행 자식1개 |
| supervisor 전체 작업 수 | 최대64개, 완료된 작업도 포함 |
| 작업 시간 | 제출부터 최대15초, 대기열 체류 포함 |
| 최종 drain | 최대15초, 이후 소유한 자식 종료·회수 |
| 요청 / 응답 header / stderr |32KiB /16KiB /16KiB |
| 응답 전체 | 해당 raw 바이트+64KiB+16KiB+4바이트 이하 |
| 작업별 저장 예약 | 해당 raw 바이트+64KiB 압축 여유+16KiB descriptor |
| 자식 RSS |384MiB,50ms 주기 high-water 검사와 응답 검사; OS의 강제 메모리 상한 아님 |
| archive 파일 수 | 기존 계약 최대1,024개, 새 등록 시 임시 파일 여유 포함 |

`ReservedStorageBudget`은 기존 단일 소유 예산의 새 하위 클래스다. 일반 raw/audit 쓰기는 모든 미사용 예약을 뺀 여유만 사용할 수 있다. 부모의 동기 저장 구간에서만 자신의 예약을 소비하며, 다른 작업의 예약은 유지한다. 실제 기록한 바이트와 아직 예약한 바이트를 이중 계산하지 않는다. 임시 파일·원본·압축본·descriptor를 모두 계산하며 물리 free-space 검사에도 예약을 포함한다.

예약과 작업 대기열은 메모리 상태다. 프로세스가 재시작하면 예약을 임의의 완료 증거로 복원하지 않는다. 자식은 캡처 파일을 쓰지 않으므로 자식 전용 경로의 숨은 출력은 없다. 부모가 남긴 파일은 기존 inventory에 포함하고, 원본/seal의 오프라인 검증 후 ticket을 재제출한다. 이미 등록된 archive는 전체 검증·재fsync 후 같은 descriptor를 반환하며 다시 저장하지 않는다. 실시간 자동 재개 서비스나 durable consumer cursor를 구현한 것은 아니다.

## 실패·중단에서 보완한 점

개발 중40개 검사에서 최종 drain timeout 후 자식 회수가 완료되지 않는1개 실패를 발견했다. timeout과 close가 중복 취소를 보내 회수 중인 `finally`를 다시 끊는 문제였다. 소유 task가 이미 취소 중이면 다시 취소하지 않고, close 호출이 취소돼도 회수를 기다리도록 보완했다. 대기 중 예약 정리는 close의 `finally`로 옮겼다. 초기 실패 로그/소스, 중간40개 통과 로그/소스, 최종43개 검사와 실행 소스를 각각 보존했다. 최종 수치는 수정 후 검증에 대한 것이다.

표준 출력 초과·잘못된 frame·다른 ticket 응답·길이/hash 불일치·gzip 손상·복원 팽창·다른 raw·worker 종료·RSS 초과·작업/최종 시간 초과·예약 부족·대기열 초과를 모두 거부한다. 저장 실패 시 임시 파일과 원본을 남기며 등록하지 않는다. descriptor rename 후 중단되면 디스크에서 보이더라도 이번 호출 성공을 추정하지 않는다. 재시작 후 재검증/재fsync를 거쳐 채택한다. 미등록 gzip이나 임시 파일은 자동 채택·삭제하지 않는다.

부모의 복원 검증·파일 쓰기·fsync는 **동기 작업**이다. 전후 및 단계별 시각을 확인해 늦은 결과를 실패 처리하지만, 실행 중인 fsync를 asyncio가 선점하지 못한다. 따라서15초가 프로세스 종료까지의 강제 wall-clock 상한이라는 주장은 하지 않는다. 취소 시 프로세스 생성/종료도 소유권을 유지해 회수를 기다린다. 실제 collector 연결 전 수신 루프 지연·watchdog·전체 저장 단계 예산과 함께 검증해야 한다.

## 다음 순서

1. raw/압축본 공통 reader와 작은 단위 시장 상태 감사를 연결한다. ticket/cursor와 감사 상태를 같은 경계에 저장하고 기존 전체 replay와 비교한다. 현재 gzip byte reader는 사용 가능하지만 압축본 기반 상태 감사는 미연결이다.
2. 실제 collector의 새 버전에 연결하고 수신/commit/압축/감사 동시 부하, 큰 장부·버스트·느린 디스크·실패 통지를 검증한다. 실제 수신을 막지 않는다는 결론은 이 단계 후에만 내린다.
3. 원본 보관 전환·삭제의 중단 복구, 저장 여유와 journal/작업/파일 수 한도까지 확인한 뒤24시간 시험 등록을 재판단한다. 현재 신규 전략 채택·24시간 운용·실주문은 시작하지 않았다.
