# 수집 부하·저장 용량·초기화 지연 진단 v1

2026-09-18 KST. **판정:24시간 기술 시험 등록은 계속 차단한다.** 짧은 실행에서의 장애 차단을 보완했지만, 감사 파일 분할 저장과 실제 입력·디스크 변동을 포함한 장시간 용량 근거가 부족하다. 이전9초 지연의 정확한 원인도 확정하지 못했다. 신규 전략·수익성·체결 검증은 수행하지 않았다.

[계측·저장 지연 차단](../../app/research/data/feed_runtime_diagnostics.py), [수집 감독자 v2](../../app/research/data/bounded_feed_collector_v2.py), [오프라인 부하 실행기](../../scripts/run_feed_load_drill.py), [검사](../../tests/test_feed_runtime_diagnostics.py), [최종 검증 기록](../../reports/validation/feed_load_v2_20260918/verification.json).

## 확인한 문제와 보완

**감사 저장 한도가 하루 수집을 지원하지 않는다.** 이전 실제12초 기록의 원본1,873,498바이트·감사126,393바이트를 전체12초 분모로 나누었다. 같은 평균 속도가 계속된다는 단순 가정에서 단일 감사 파일32MiB는 약53.10분에 도달한다. 짧은 실행용 한도를 더 크게 적는 것만으로 해결했다고 판정하지 않는다. 분할 파일·확정 구간·재생·전체 저장 예산을 함께 설계해야 한다.

**동기 저장이 느리면 별도 감시 작업도 같이 밀린다.** v2는 원본 append, 원본 commit·처리, 감사 쓰기·fsync, 전체 flush의 벽시계 시간과 프로세스 CPU 시간을 계측한다. 개별 단계 또는 전체 flush가500ms를 넘으면 정상 완료 집계를 하지 않고 실패 상태를 유지한다. 원본의 수신→commit 간격1초도 저장 전후에 검사한다. 저장 전에는 기준 이내였지만 저장 중 초과한 경우를 포함한다. 이는 호출이 반환된 뒤의 차단이며 멈춘 시스템 호출을500ms에 강제 종료한다는 뜻은 아니다.

개별 단계만 검사하면 원본300ms+감사300ms가 각각 통과하는 허점이 남는다. 자체 검토에서 이 경우를 추가했고, 전체 flush 기준으로 차단했다. 원본·감사 바이트가 디스크에 남았더라도 감독자의 실패를 정상 운영으로 바꾸지 않는다.

**저장 실패 뒤의 수신 루프에도 실행 기회 양보가 필요했다.** 정상 수신 경로에는 있던 양보가 실패 후 프레임을 버리는 분기에는 없었다. 대기 중 메시지가 계속 즉시 반환되면 소켓 close 작업이 밀릴 수 있어, 실패 분기도 매 프레임 뒤 양보하도록 보완했다. 저장하지 못한 프레임을 포함해 수신 UTC 상한도 갱신한다. 닫기 응답 대기 중 메시지가 계속 들어오는 검사에서 종료·누락 집계·관측 시각 보존을 확인했다.

기존 [v1 수집기](BOUNDED_FEED_COLLECTOR_V1.md)와 그 결과를 수정하지 않았다. 새 v2 감독자는 기존 전송·재시도·원래 종료 계약을 유지한다. v2는 이번에 **오프라인으로 검증**했으며 새 실시간 시장 수집은 실행하지 않았다.

## 사전 고정한 최종8개 시나리오

[실행 계획](../../reports/validation/feed_load_v2_20260918/scenario_plan.json), [전체 결과](../../reports/validation/feed_load_v2_20260918/summary.json). 사례마다 별도 자식 프로세스·원래2초 창을 사용했다. 느린 저장/디스크 부족은 주입한 오류이며 실제 디스크를 채우거나 장치를 손상시키지 않았다.

| 시나리오 | 최종 관측 | 판단 |
|---|---|---|
| 목표 public200프레임/초 | 전체329프레임, 실제164.5/초, 최대 원본 대기15개 | 원래 종료까지 처리, 감사 오류 없음 |
| 목표 public2,000프레임/초 | 전체3,041프레임, 실제1,520.5/초, 최대 대기84개 | 원래 종료까지 처리, 감사 오류 없음 |
| 원본 commit에650ms 지연 | 해당 단계 약663ms | 실패 중단, 재시도 없음 |
| 감사 저장에650ms 지연 | 해당 단계 약660ms | 실패 중단, 정상 처리 순번 미전진 |
| 원본·감사에 각각300ms 지연 | 전체 flush 약623ms | 합산 지연으로 실패 중단 |
| snapshot 초기화에900ms 동기 정지 | 감시 지연 오류 확인 | 실패 중단 |
| 대기 상한을8개로 줄여 초과 유발 | 대기8개 뒤 추가 입력 거절 | 원본 꼬리 보존, 실패 중단 |
| 원본 commit에ENOSPC 주입 | 디스크 부족 오류 확인 | 실패 중단, 재시도 없음 |

두 정상 부하의 프로세스 최고 RSS는 각각 약31.09MiB와32.75MiB였다. 이는 짧은 프로세스 전체의 관측 최대값이다. 메모리가 하루 동안 이 범위에 머문다는 입증은 아니다. 호가 장부 크기는 배치 후 표본만 측정하며 처리 중 순간 최대치를 보장하지 않는다. 지연 통계는 고정 크기 histogram과 최근16개 느린 호출로 제한하고, 정상 처리 배치는 저장 후 메모리 목록에서 제거했다.

**목표2,000/초를 실제로 처리했다고 주장하지 않는다.** 작은 모의 bookTicker/depth와 초당1개 mark를 사용했고, 실제 생성·수신량은 위 표처럼 목표보다 작았다. 생성기가 같은 이벤트 루프를 공유하며 느려질 수 있으므로 외부 거래소의 독립적인 입력 압력을 재현하지 않는다. 큰 snapshot·큰 depth 메시지·소켓 backlog·TCP backpressure·가격의 실제 신선도는 별도 검증이 필요하다. 정상 종료는 이 고정 시나리오의 처리 결과이며 성능 한계 인증이 아니다.

[첫 부하 실행](../../reports/validation/feed_load_20260918/summary.json)과 당시 소스3개도 보존했다. 첫 실행은7개 사례였고 이후 합산 지연 사례와 차단을 추가했다. 이번 작업 전체는 부하 사례15회·별도 새 프로세스 초기화6회이며, 최종 버전 근거는8개+3개다. 새 네트워크 요청·주문은 모두0건이다.

## 기존9초 지연은 어디까지 밝혔는가

[기존 기록의 공백 분석](../../reports/validation/feed_load_v2_20260918/historical_gap_analysis.json)은 REQUEST→다음 수신 사이 약9.06초 공백을 재확인했다. 당시 호출 스택과 REST 단계 계측이 없어, 그 시간에 어떤 호출이 멈췄는지를 사후에 확정할 수 없다.

최종 실행에서 별도 새 Python 프로세스3개를 사용해 httpx import, websockets import, 기본 TLS 클라이언트 생성, 모의 HTTP 요청을 측정했다. httpx import는 약22.10~22.36ms, TLS 클라이언트 생성은 약17.52~17.76ms였고9초 현상은 재현되지 않았다. OS 파일 캐시를 지운 실험이 아니며 실제 DNS·네트워크 연결·원격 응답은 포함하지 않았다. 이 결과로 초기화나 운영체제 지연을 원인 후보에서 확정적으로 제외하지 않는다.

주입한 정지 사례에서는 별도 타이머로 호출 스택을 남겼다. [느린 원본 저장 스택](../../reports/validation/feed_load_v2_20260918/slow_raw/stack_sample.txt)은 commit의 주입된 sleep 위치를, [초기화 정지 스택](../../reports/validation/feed_load_v2_20260918/startup_block/stack_sample.txt)은 snapshot 위치를 보여 준다. **유사한 실패 유형을 계측할 수 있음을 확인한 것이며, 이것이 과거9초 지연의 원인이라는 뜻은 아니다.**

## 저장 용량 진단

[상수 속도 시나리오](../../reports/validation/feed_load_v2_20260918/capacity_projection.json). 이전12초 창에는 연결 준비·재연결 공백도 포함돼 있다. 해당 전체 평균을 그대로 하루로 늘린 값이며 예측값이나 확보된 용량 보장이 아니다. 메타데이터·체크포인트·추가 진단 파일·입력 변화는 더 필요하다.

| 이전 평균 대비 저장 속도 | 원본+감사 하루 환산 | 관측 여유 공간과 비교 |
|---|---:|---|
| 1배 | 약13.41GiB |16GiB 여유 기준을 남긴 가용량 약16.02GiB 안이지만 추가 여유가 작음 |
| 2배 | 약26.82GiB | 가용량 초과 |
| 5배 | 약67.05GiB | 가용량 초과 |

당시 디스크 여유는 약32.02GiB였고 정책상16GiB를 남겨야 한다. 물리적 가용 공간과 원본64GiB 정책 한도는 서로 다르다. 모든 시나리오에서 단일 감사32MiB 한도를 초과한다. 현재32MiB 한도와16GiB 여유 기준을 통과시키기 위해 임의로 완화하지 않았다.

## 검증과 실행 방법

신규28개 포함 관련 고유484개 검사 통과(연구424개·수집/전송/진단60개, 기존 두 런타임에서 분리 실행). 새 감독자에서 기존15개 통합 계약을 다시 검사한 사례도 신규28개에 포함된다. 저장 전후 경계는 합성 시계로 정확히 검사했고 지연 주입·스택·프로세스 메모리는 실제 로컬 시간으로 측정했다. 중복 모듈을 포함한 초기 회귀 실행 로그는 보존하고, 최종 회귀 목록은 중복을 제거해424개를 확인했다. 검사 수를 중복 실행으로 늘리지 않았다.

기존 동결 코드·산출물 해시 대조1,253건(고유984경로) 일치. [검증 기록](../../reports/validation/feed_load_v2_20260918/verification.json).

```bash
.venv/bin/python -m unittest tests.test_bounded_feed_collector tests.test_public_feed_transport tests.test_feed_runtime_diagnostics
.venv/bin/python scripts/run_feed_load_drill.py --output reports/validation/NEW_UNIQUE_DIRECTORY
```

다음 공개 확인에 사용할 [v2 실행기](../../scripts/probe_guarded_feed.py)도 준비했으며, 이번에는 import/CLI 확인만 했다. 최대120초 제한을 유지한다. 기존 실제 수집 v1 결과를 v2의 실제 수집 결과로 바꿔 표시하지 않는다.

## 다음 순서와 완료 조건

1. **감사 파일 분할 저장과 원본+감사+부가 기록의 전체 저장 예산.** 분할/회전 중 강제 종료, 확정 prefix만 재생, 남은 디스크 기준, 재연결 시 예산 유지까지 검사한다. 실제24시간 예상량에 대한 여유를 확보하기 전에는 등록하지 않는다.
2. **v2의 단계적 공개 부하 확인과 초기화/외부 입력 정지 계측.** 저장·이벤트 루프·실제 전송 초기화의 기록을 함께 남기고, 실제 수신 지연과 내부 처리 지연을 구분한다. 짧은 모의 생성률을 실거래소 입력 보장으로 쓰지 않는다. 기존9초 지연의 확정 원인을 꾸며내지 않는다.
3. 근거가 모이면 소스·복구·용량·시계·전체 관측 이력을 묶어24시간 기술 시험 등록 여부를 다시 판단한다. 수집기의 자동 프로세스 재시작·외부 경보·계좌/주문 통합·체결 모형·전진 수익성 평가는 별도 미완료 조건으로 남는다.
