# 별도 증분 감사 작업자와 부모 체크포인트 저장 v1

2026-09-18. 상태: **오프라인 부품 검증 통과. 실제 collector 통합·동시 부하 검증은 다음 단계다.**

시장 상태를 재생하는 계산을 별도 프로세스로 옮겼다. 부모는 기존 저장 소유권과 체크포인트 잠금을 유지한다. 자식은 원본 또는 gzip의 확정 구간과 이전 상태를 읽고 다음 상태를 반환하며, 부모가 요청 연결·순서·상태 구조를 검증한 뒤 저장한다. 신규 전략 채택이나 수익성 검증의 진전으로 해석하지 않는다.

근거: [검증 기록](../../reports/validation/background_incremental_audit_20260918/verification.json), [시험 계획](../../reports/validation/background_incremental_audit_20260918/drill/plan.json), [실행 요약](../../reports/validation/background_incremental_audit_20260918/drill/summary.json). 앞 단계의 [증분 감사](INCREMENTAL_FEED_AUDIT_V1.md)와 [압축 작업자](BACKGROUND_SEGMENT_ARCHIVE_V1.md)는 수정하지 않았다.

## 계산·저장 책임

1. 제출 시 입력을 복사하고 확정 감사 구간의 연속성을 검사한다. 실행 중 작업을 포함해 최대 2개만 받고, 체크포인트 교체 공간 8MiB를 작업마다 미리 예약한다. 기존 체크포인트와 실패한 임시 파일의 실제 점유량도 계산한다.
2. 실제 실행 시점에 부모의 최신 체크포인트를 요청에 담는다. 대기열에 넣을 때의 오래된 상태를 사용하지 않는다. 요청에는 작업 번호, 입력, 상태 checksum, 구현 파일 hash, 메모리 한도가 포함된다.
3. 자식은 기존 재생 코드와 상태 codec을 그대로 사용한다. 잠금을 취득하거나 journal/checkpoint를 쓰지 않는다. 원본/gzip 선택은 명시적이며 손상 시 다른 쪽으로 자동 전환하지 않는다.
4. 자식을 회수한 부모는 요청 checksum·이전 영수증·구현 hash·상태 schema·후속 revision·입력 cursor·진행량을 검사한다. 메모리 속 기준 상태뿐 아니라 디스크의 기존 체크포인트가 그대로인지도 확인한다.
5. 부모가 예약 공간 안에서 임시 파일 쓰기 → 파일 fsync → 원자적 교체 → 디렉터리 fsync를 수행한다. 제출 시점부터의 기한도 확인한 뒤 완료 영수증을 공개한다. 뒤늦게 저장이 끝나도 기한을 넘으면 성공을 반환하지 않는다.

읽기 전용은 제공한 코드와 인터페이스의 속성이다. OS 파일 권한 격리나 악성 자식에 대한 보안 경계가 아니다. **부모는 시장 재생을 독립적으로 반복하지 않는다.** 고정한 자식 코드를 신뢰하며, 구조를 만족하도록 조작한 임의의 시장 상태까지 독립적으로 증명한다고 주장하지 않는다. 원본 해시 검증·시장 재생 자체의 의미 검사는 자식의 기존 감사 코드가 담당한다.

저장된 체크포인트는 기존 v1 형식과 재생 구현 계약을 유지한다. 이번 작업자/전송 코드의 hash는 각 요청과 별도 검증 기록에 묶는다. 체크포인트의 알고리즘 계약이 이번 전송 코드까지 새로 포함한다고 해석하지 않는다.

## 한도와 실패 처리

| 항목 | 현재 한도·처리 |
| --- | --- |
| 감사 작업자 | 1개 프로세스, 실행 포함 대기 2개, 실행 전체 작업 64개 |
| 시간 | 제출부터 작업 완료까지 15초, 최종 drain 15초 |
| 입력·응답 | 요청 10MiB, 입력 참조 512KiB, 응답 8MiB+64KiB, stderr 16KiB |
| 저장 상태 | 체크포인트 최대 8MiB; 앞 단계의 상태·구간별 처리 한도 유지 |
| 메모리 | 자식 RSS 384MiB, 50ms 간격 high-water 감시와 반환 시 확인; 강제 물리 상한은 아님 |
| 실패 | 작업자 종료·형식 오류·순서 불일치·용량/시간 초과에서 소유자와 공통 저장 예산을 실패 상태로 고정 |
| 종료 | 생성 중 취소·중복 close·finish 취소에서도 자식 kill/drain/reap 및 대기 예약 해제 |
| 재개 | 마지막 외부 영수증에 연결되는 같은 체크포인트 또는 바로 다음 상태만 수동 재개; 자동 서비스 재시작은 미구현 |

공통 저장 예산은 압축과 감사를 합쳐 **예약 2개**다. 이번 시험은 압축 1개+감사 1개를 함께 예약하고, 둘이 대기하는 동안 활성 journal을 저장했다. 각 감독자의 대기열을 각각 2개씩 채울 수 있다는 뜻이 아니다. 다음 collector는 두 종류의 작업을 함께 배정하는 규칙이 필요하다. 예약 초과는 조용히 밀어 넣지 않고 전체 실패로 처리한다.

부모의 JSON/state 검증·checksum·fsync는 동기식이다. 늦은 성공을 거부해도 이미 실행 중인 동기 저장 호출을 중간에 끊을 수는 없다. 따라서 15초 설정이 event loop 정지 시간의 강제 상한은 아니다.

## 검증 결과

- 관련 고유 **813개** 검사: 기존 776개와 신규 37개. 연구 회귀 424개는 Python 3.12, 실행/기존 부품/신규 검사는 Python 3.14에서 수행했다. 실패·오류·건너뜀 0.
- 기존 공개 2개 epoch의 원본 **8,577개**, 감사 **898개**와 버퍼 복구를 포함한 합성 원본 44개를 raw/gzip 각각으로 재생했다. 전체 재생과 17개 의미 항목이 모두 일치했고, raw/gzip의 payload chain도 일치했다. 비교 실행은 최종화 포함 작업자 168회다. 새 시장 관측은 아니다.
- 실제 부모 SIGKILL 4곳: 제안 검증 직후, 임시 체크포인트 fsync 직후, 교체 직후, 디렉터리 fsync 직후. 앞 2곳은 revision 5, 뒤 2곳은 revision 6으로 재개했다. 나머지를 실제 작업자로 완료한 뒤 전체 재생과 일치했다. 각 부모 종료 전에 감사 자식은 이미 정상 회수돼 있었다.
- 별도 hang fixture 작업자에 실제 SIGKILL 1회: 이전 체크포인트 보존, 성공 영수증 없음, 자식 회수, 예약 해제, 실패 상태 고정을 확인했다. 이 사례는 전송/감독 오류 경로 시험이다.
- 저장 후 기한 초과, 잘못된 요청/상태/마지막 cursor, 오래된 부모 상태, 외부 체크포인트 변경, stdout/stderr 초과, 작업자 오류 및 취소를 검사했다.
- 이전 **6,122건** hash 대조, 고유 경로 5,853개가 일치했다. 이전 공개·실험·검증 파일을 보존했다.

| 재생 자료 | raw 작업 수 / 부모 최대 ms | gzip 작업 수 / 부모 최대 ms |
| --- | --- | --- |
| 합성 버퍼 사례 | 45 / 2.24 | 45 / 2.86 |
| 공개 epoch-00 | 4 / 25.73 | 4 / 25.67 |
| 공개 epoch-01 | 35 / 32.95 | 35 / 33.08 |

작업 수에는 최종화가 포함된다. 부모 시간은 응답 수신 후 검증부터 저장 완료까지이며 요청 생성 시간·전체 job 시간은 제외한다. 전체 비교에서 자식 최대 RSS는 37.125MiB였다. 이 수치는 해당 자료·환경의 관측값이며 최악 지연·장시간 메모리 상한 인증이나 이전 동기 구현 대비 공정한 속도 비교가 아니다.

## 남은 작업과 완료 판단

1. 실제 collector에 확정 구간 인계·압축·증분 감사를 연결한다. 공용 예약 2개 안에서 처리 순서를 정하고, 작업자 오류가 수신/REST 종료까지 전달되는지 확인한다.
2. 독립 생산자, 큰 장부와 버스트, 실제 fsync, 압축/감사 계산이 겹치는 부하를 검증한다. 입력 유실·순서·대기열·event loop 지연·최종 감사 cursor를 함께 판정한다. 이번 gated overlap만으로 이 항목을 완료 처리하지 않는다.
3. 원본 보관 전환과 중단 복구, 실제 공간 회수 조건, 장기 파일/작업 개수와 처리율 한도를 설계·검증한다. 현재 64개 작업 한도는 장기 수집에 충분하다고 인정하지 않는다.
4. 위 근거와 전체 관측 이력을 반영한 뒤 장시간 기술 시험을 등록한다. 현재 수집기 최대 120초, 24시간 미등록, 새 전략 미채택을 유지한다.

자동 주문·private 요청·새 네트워크 수집·원본 삭제·공간 회수는 모두 0이다. 기존 시장 상태를 감사 재생하는 기능이며 실시간 거래 상태의 복원이 아니다. 로컬 프로세스 종료를 시험했으며 정전·디스크 고장을 인증하지 않았다.
