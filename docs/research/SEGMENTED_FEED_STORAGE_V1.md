# 감사 분할 저장·실행 전체 예산·프로세스 종료 복구 v1

2026-09-18. 범위: 연구 자료 수집의 저장 적격성. 새 전략, 수익률, 체결 모형 또는24시간 운용 승인 결과가 아니다.

## 해결한 문제

이전 수집기는 원본에만 실행 전체64GiB 한도를 적용했고, 감사는 epoch마다 단일32MiB 파일이었다. 기존12초 평균을 단순 연장하면 감사 한도에 약53분 만에 도달했다. 메타데이터·감사·부가 기록의 합계와 체크포인트 교체 중 임시 공간도 한 예산으로 관리하지 못했다.

새 구현은 원본과 감사를 같은 해시 사슬·체크포인트 형식으로 나누어 저장한다. 원본 기본 파일 크기는128MiB, 감사/감독 기록은32MiB이며,32MiB는 감사 전체 상한이 아니라 파일 전환 기준이다. 실행 전체의 모든 정규 파일에64GiB 한도를 추가 적용한다. 기존 원본 전용64GiB 정책보다 엄격한 추가 제약이며, 동결된 전진 시험 등록 계약을 변경하거나 등록 완료로 해석하지 않는다.

## 저장 계약과 코드

- [공유 저장 예산과 분할 기록](../../app/research/data/shared_feed_storage.py): `SharedStorageBudget`, `BudgetedJournal`, `SegmentedAudit`.
- [분할 감사 재생](../../app/research/data/segmented_feed_audit.py): 확정 감사 payload를 원본과 대조한다. 거대한 단일 임시 JSONL로 합치지 않는다.
- [새 수집 경로](../../app/research/data/segmented_feed_collector.py): 기존 v2의 비동기 연결·취소·종료 제어와 저장 지연 감시를 재사용한다. 새 저장 경로는 이번에 오프라인에서만 검증했다.
- [저장·수집 검사](../../tests/test_segmented_feed_storage.py), [강제 종료/재연결 훈련](../../scripts/drill_segmented_feed_storage.py), [합성 부하 훈련](../../scripts/drill_segmented_feed_load.py).

실행 루트는 한 소유자와 하나의 로컬 파일시스템에 한정한다. 협조적 배타 잠금으로 두 번째 예산 소유자를 차단하며 외부 프로세스의 임의 파일 수정은 지원하지 않는다. 심볼릭 링크·다른 파일시스템·특수 파일을 거부한다.

예산에는 원본, 감사, 감독 기록, plan, storage 계약, 메타데이터, 체크포인트, 최종 결과, 실패 후 남은 꼬리·임시 파일을 포함한다. 체크포인트 교체 전에는 기존 파일과 새 임시 파일이 동시에 차지하는 전체 크기를 검사한다. 정상 쓰기는 변경된 파일 크기만 갱신하고, 시작/복구/새 epoch 경계에는 전체 파일 목록을 다시 합산한다. 새 epoch가 예산을 초기화하지 않는다.

이는 **논리적 파일 바이트 한도**다. 실제 파일시스템의 할당 단위·디렉터리 비용을 같은 값으로 단정하지 않는다. 별도로 매 쓰기 전에 실제 여유 공간이16GiB+예정 증가량+64KiB 이상인지 검사한다. 다른 프로그램의 동시 저장까지 예약하거나 ENOSPC를 예방한다고 보장하지 않으며, 실제 쓰기·fsync 실패도 처리한다.

쓰기 실패는 공유 예산과 해당 경로를 실패 상태로 고정한다. 다른 기록 경로도 계속 쓰지 못한다. 최종 결과를 저장할 공간조차 없으면 메모리 반환값에 `result_persisted=false`로 알리고, 한도를 우회하는 다른 파일을 만들지 않는다. 훈련 보고서는 수집 루트 밖에서 별도 검사기가 저장한 증거이며 이러한 우회 저장 경로가 아니다. 저장된 결과의 `storage_before_result`는 결과 파일을 쓰기 직전, 호출자 반환값의 `storage_after_result`는 쓰기 이후 용량이다.

## 복구 의미

기존 체크포인트가 가리키는 전체 확정 부분을 검증한 뒤에만 읽는다. 원본과 감사의 run ID와 원본 순번·해시·관찰 결과를 대조한다. 손상된 확정 감사 파일은 정상 관찰로 사용할 수 없다. 미확정 꼬리와 남은 체크포인트 임시 파일도 조용히 무시하지 않고 감사 오류로 남긴다.

프로세스 강제 종료가 체크포인트 rename 이후였다면, 호출자가 성공 응답을 받기 전의 새 체크포인트가 보일 수 있다. 복구기는 이를 검증하고 다시 동기화할 수 있지만, 이를 과거 실행 중 성공 응답이 있었다는 증거로 바꾸지 않는다. 원본만 확정되고 감사가 없는 경우는 미감사 원본으로 남는다. 미확정 바이트를 잘라내거나 덮어쓰지 않는다.

**저장 복구와 실시간 재가동은 다르다.** 이번 구현은 디스크 기록 복구와 같은 프로세스 안의 유한 재연결을 검증한다. 프로세스 재시작 후 호가·연결·단조 시계·원래 종료 시각·재시도 상태를 복원해 자동으로 네트워크 수집을 재개하는 서비스는 구현하지 않았다. 정전·저장장치 고장·파일시스템 장애 보장도 아니다.

## 남은 제한과 다음 순서

1. **새 저장 경로의 공개 단기 수집 확인과 장기 감사 비용 측정.** 최대120초 제한은 유지한다. 기존 공개 운용 결과를 이번 경로의 공개 성공으로 대체하지 않는다. 재생은 큰 원본/감사를 한 번에 메모리에 합치지 않지만, 감사 구간 계산은 관찰 시점별 목록을 보유하므로 하루 규모의 메모리·시간 한도를 추가 검증해야 한다.
2. **24시간 용량 계획과 부하 상한.** 이번 형식은 감사에 해시/체크포인트를 추가해 이전 JSONL보다 저장 비용이 늘어난다. 이전1배/2배 추정이나 작은 합성 실행만으로 충분한 공간을 판정하지 않는다. 실제 입력 크기·변동·부가 기록·회전 비용을 반영해 여유 공간을 재산정하고 중단 조건을 확인한다.
3. **계측과 시험 등록.** 과거 약9초 지연의 원인은 여전히 미확정이다. 새 계측 근거와 관측 이력을 묶고 종료/복구 경계를 검토한 뒤 고정24시간 기술 시험의 등록 여부를 판단한다.

24시간 시험, 체결 모형 적격성 확증, 전략 전진 수익성 검증, 실계좌 자동 운용은 아직 시작하지 않는다. 당장의 다음 작업은 후보 전략을 더 만드는 일이 아니라, 이 수집 기반이 실제 짧은 공개 입력과 장기 감사 규모를 감당하는지 확인하는 것이다.
