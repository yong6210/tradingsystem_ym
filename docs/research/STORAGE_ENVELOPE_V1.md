# 저장량·독립 생산자 부하·압축 가능성 v1

2026-09-18. 최대120초 확인용 v5의 다음 제약을 점검했다. 기존 수집기/정책/검증 자료는 변경하지 않았고, 새 공개 데이터 요청·실주문·전략 채택도 없다.

## 확인한 허점과 개선

이전 가짜 스트림은 `recv()` 호출에 맞춰 다음 데이터를 만들었다. 수집기가 저장 때문에 느려지면 생산도 느려져서 외부 대기열 누적을 시험하기 어려웠다. 새 오프라인 fixture는 별도 스레드에서100ms 고정 주기로 데이터를 만든다. 수신기가 멈춰도 생산하며, 큐가 넘치면 버리고 정상인 척하지 않고 오류를 반환한다.

생산량·수신량·종료 시 큐 잔량·최고 큐 길이·큐 체류 시간·생산자의 예정 시각 대비 지연을 따로 기록한다. Python GIL은 공유하므로 외부 네트워크와 완전히 독립적이지 않다. 고정 합성 가격/순번/시각을 사용한 제어 흐름·저장 부하 시험이며 실제 거래소 시각·호가 우선순위·체결 모형이 아니다.

저장 계산도 전체 평균 외에 **정렬 경계에 걸친 순간 집중을 잡는 이동1초 최대값**을 추가했다. 기존 공개4회(합계96초)의 전체 원본/감사 파일을 검증하고, 논리 파일 크기와 `stat` 할당 블록을 분리했다. 할당 블록은 APFS snapshot/공유 블록까지 포함한 독점 물리 사용량이 아니다.

## 고정 부하 시험 결과

각 시나리오는 별도 프로세스에서 순서대로 실행했다. 실제 원본·감사 fsync, 한쪽1,000개씩 총2,000개 호가, 최대512MiB 캡처 예산, 작업자45초 외부 종료 한도였다. 정상 시나리오의 생산량/예정량도 검사했고 결과에 맞춰 입력률을 낮춰 재실행하지 않았다.

| 시나리오 | 고정 창 | 생성/수신 프레임 | 최고 큐 | 결과 |
|---|---:|---:|---:|---|
| 큰 장부, public200개/초 설정 |4초|804 /804|20|예정 종료·감사 완료|
| 재접속 후 감사와 수집 겹침 |8초|1,407 /1,407|20|새 epoch 중 이전 실제 감사 실행·완료|
|100ms마다200개, public2,000개/초 설정 |4초|8,004 /8,004|200|예정 종료·감사 완료|
| 큐128개에 큰 버스트 |4초 계획|129 /1|128|오류로 조기 중단|
| 원본 commit에650ms 지연 주입 |4초 계획|222 /107|120|저장 지연 감지·조기 중단|

프레임 수는 public와 market 합계이며 재접속 공백도 고정 창에 포함한다. 실패 시 미수신 자료를 수신한 원본처럼 취급하지 않는다.650ms 주입 동안 생성량은101→222로 늘어 실제로 대기열이 쌓였다. 버스트 정상 사례의 최고 큐 체류38.31ms, 최고 동기 flush11.09ms, 부모 RSS33.91MiB였다. 다섯 사례 전체에서 부모 최대 RSS35.11MiB였다. 이 짧은 시험값은 서비스 최대 처리량이나 메모리 상한 인증이 아니다.

동시 감사 사례는 첫 감사의 시작을 두 번째 snapshot 시점까지 오프라인 gate로 지연한 뒤 실제 재생/해시 검증을 수행했다. 단순히 잠든 프로세스를 동시 감사라고 세지 않았다. 두 번째 수집이 활성인 동안 감사가 완료된 시각을 보존했다. 실제 네트워크 버퍼의 overflow 통지 방식은 이 fixture와 다를 수 있다.

## 저장 공간 판단

측정 당시 물리 여유는16GiB 보존분을 제외하고 **15.72GiB**였다. 기존4회 중 최대 달력 평균은126,925bytes/s, 이동1초 원본+감사 record 최대값은612,159bytes였다. 아래는 각각의 관측값이 하루 내내 유지된다고 가정한 계산에, 미검증 공학적 여유64MiB를 추가한 것이다.

| 가정 | 하루 필요량 | 현재 공간 대비 |
|---|---:|---|
| 최대 관측 평균1배 |10.28GiB|단순 공간 계산상 맞음|
| 최대 관측 평균2배 |20.49GiB|4.77GiB 부족|
| 최대 이동1초 관측량1배를 계속 유지 |49.32GiB|33.60GiB 부족|
| 최대 이동1초 관측량2배를 계속 유지 |98.58GiB|물리 여유와64GiB 논리 예산 모두 초과|

**관측 최대값은 시장의 상한이 아니다.** 평균에는 연결/재접속/종료 공백이 포함된다. 이동1초 값은 애플리케이션 수신 시각과 감사 관찰 시각 기준이며 디스크 쓰기 속도가 아니다. 하루 metadata 성장·파일시스템 부가 비용·checkpoint 재작성 I/O·다른 프로그램의 공간 소비를 보장하지 않는다. 따라서 가정하의 최대 시간 계산이 나와도 장시간 실행 허용 시간으로 사용하지 않는다. 새 계산 모듈은 진단용이며 실시간 입력률 제한기/장기 운용 승인기로 연결하지 않았다.

## 원본 보존 상태에서 압축 가능성 확인

기존 공개4회의 닫힌 원본·감사·감독 segment만 새 벤치마크 디렉터리에 gzip level1/6으로 각각 저장했다.256KiB 버퍼, 전체 새 압축 파일32MiB 한도, 파일 flush/fsync 뒤 전체 복원·SHA256 대조를 수행했다.

| 설정 | 압축 후 segment 크기 / 원래 크기 |
|---|---:|
|gzip level1|14.71~17.72%|
|gzip level6|12.25~14.64%|

모든 파일의 복원 바이트 수·해시가 일치했고 원본 해시도 변하지 않았다. 입력 원본은 삭제/교체하지 않았으므로 확보한 공간은0이다. 보조 파일을 그대로 둘 때의 예상 보관량도 별도로 기록했다. 측정 시간은 해당 호스트의 통제하지 않은 OS 캐시에서 파일 fsync까지 포함한 값이며, 디렉터리 fsync/원자적 등록/장애 복구/실시간 압축 지연은 검증하지 않았다. 이 압축률을 미래24시간 자료에 그대로 적용해 적격 판정을 내리지 않는다.

## 다음 구현 순서

1. **닫힌 작은 구간을 대상으로 한 압축 보관 계약**: 원본·압축본·복원 해시 결합, 작성 중 임시 파일까지 공통 예산 계산, 원자적 등록, 각 중단 지점에서 복구. 우선 level1을 고정한 후보로 검증하고, 기존 사용자 자료/동결 보고서는 보존한다.
2. **작은 단위의 감사와 재생**: 압축 구간 읽기에도 원래 순번·hash·시간 창·상태 인계를 보존한다. 이전 하루 전체 감사185.67초가15초 작업 제한을 넘는 문제를 풀어야 한다. 단순히 시간 한도를 늘리는 것으로 완료 처리하지 않는다.
3. 새 구조의 동시 저장·압축·감사 부하와 실패 전파, 최악의 일시적 이중 보관량을 다시 측정한 뒤 저장 경로/용량과24시간 기술 시험 등록을 판단한다.

고유642개 검사(기존628+신규14), 고정 부하5개, 압축8개 조합의 전체 복원 대조, 이전2,071건/고유1,802경로 해시 확인을 완료했다. 최대120초 수집 제한과24시간 시험 미등록 상태는 유지한다. 수익성 검증·새 모델 채택·실주문은 미진행이다.
