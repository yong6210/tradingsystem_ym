## 원본 → 저장 확인 → 처리 → 관찰

1. 두 수신 작업과 감시 작업이 같은 이벤트 루프에서 원본을 순서대로 넘긴다. 원문·채널·연결 세션·process epoch·수신 단조 시각·수신 UTC 나노초를 [영속 로그](DURABLE_CAPTURE_LOG_V1.md)에 기록한다.
2. 호출자가 이후 객체를 바꾸더라도 저장된 원본과 처리 입력이 달라지지 않도록 JSON 복사본을 소유한다. 처리 대기 상한2,048개를 넘기면 조용히 버리지 않고 실패 상태로 중단한다.
3. 기본50ms 간격으로 대기 기록을 commit한다. 원본과 체크포인트의 fsync 완료 순번/시각을 받은 다음에만 파싱·장부/market 상태 갱신을 실행한다. 파일 쓰기 또는 commit 실패 시 대기 입력은 판단에 공개하지 않는다.
4. 배치 안의 사건을 전부 처리한 뒤 실제 단조 시각으로 사용 가능 여부를 관찰한다. 배치 중간에 잠깐 정상인 상태를 종료 사건보다 먼저 공개하지 않는다. 후속 메시지로 과거 판단 시각을 덮지 않는다.
5. 원본 연결 해시와 `batches.jsonl`의 첫/마지막 순번, commit 해시, 완료 시각, 관찰 시각을 대조해 재생한다. 전체205개 관찰·이벤트 집계·오류 상태가 일치했다. [별도 경계 대조](../../reports/validation/durable_market_feed_v2_20260917/boundary_checks.json)에서도 수신≤저장 완료≤관찰 시각과 종료 경계 위반0이었다.

50ms는 실행기의 예약 간격이며 최악 지연 보장이 아니다. 동기 디스크 처리가 이벤트 루프를 지연시키는 정도는 실제 감시값으로 검사해야 한다. 이 구조의 장시간 처리량·디스크 피크·메모리 상한 적합성을 입증한 것은 아니다.

처리 감사 파일은 실행 중 flush하고 종료 때 fsync한다. **원본만 살아 있고 감사 파일이 유실되면 당시 사용 가능 시각을 임의로 추정하지 않는다.** 원본 prefix는 복구할 수 있지만 동일한 온라인 관찰 이력을 확정할 수는 없다. 감사 기록까지 장애와 함께 복구·대조하는 통합 경로는 다음 단계다.

## 데이터 사용 조건과 차단

관찰이 적격하려면 아래 조건과 오류 없음·중단 전·고정 종료 전을 모두 만족해야 한다.

- L2: snapshot과 갱신 사슬 연결, 마지막 유효 depth의 로컬 수신 나이1초 이내. 스냅샷 fsync가 오래 걸려 `book.available_ns`가 최신처럼 보여도 원래 depth 수신 나이를 별도로 검사한다.
- market 연결: 연결 세션이 유효하고 마지막 유효 market 수신이3초 이내다. 이것은 로컬 생존성 근거이며 거래소의 전체 체결 전달을 보장하지 않는다.
- mark: 마지막 유효 mark 수신이3초 이내다. 같은 사건의 같은 내용은 중복으로 세고 수신 나이를 갱신하지 않는다. 사건 시각 역행 또는 같은 시각의 내용 충돌은 차단한다.
- 시계/루프:250ms 간격 감시,500ms 초과 지연과 UTC/단조 변화량100ms 초과 차이를 차단한다. 감시도500ms 이상 오래되면 부적격이다. UTC 절대 시각 오차나 네트워크 패킷 도착 지연의 인증은 아니다.
- 영속 원본: 해당 처리 순번까지 fsync 확인을 받아야 한다. 구문/채널/종목/순서·값이 잘못됐으면 원본을 남긴 채 실패 상태를 유지한다.

aggTrade가 없는 시간 자체는 결측으로 단정하지 않는다. 같은 ID의 같은 숫자 내용은 한 번만 반영하고 충돌/역행을 차단한다. 관측 ID가 건너뛰면 `AGGREGATE_ID_GAP_UNVERIFIED`로 사용을 중단한다. 모든 ID의 연속성이 공식적으로 보장된다는 주장이 아니라, 현재 구현이 그 구간의 완전성을 확인하지 못했다는 보수적 처리다. 실제 필드 파서는 보존한 BTCUSDC 원본과 이번 수신으로 검사했으며 현물 API의 규칙으로 대체하지 않았다.

시작 시 원래 종료 시각을 원본 `RUN_WINDOW`에 기록한다. 관찰 시각이 그 종료 시각 이상이면 모든 시세가 신선해도 적격이 아니다. `STOP`과 양쪽 `END`를 영속 반영한 뒤 소켓을 닫고, 그 사이 수신 프레임은 `CLOSING_WS`로 저장만 한다. 원본은 연결 재개나 새 거래를 지시하는 실행 명령으로 취급하지 않는다.

## 이번에 다룬 오류와 남은 범위

검사한 것은 저장 전 미반영, fsync 오류, 대기열 상한, 원본 복사본 격리, 늦은 REST 반영, 오래된 depth/mark/감시, mark 중복/역행, trade 중복 충돌/의심 공백, 잘못된 종목·수치·방향, epoch 변경, 시계 점프·루프 지연, 연결 종료·종료 프레임·고정 종료 시각이다. 재생은 같은 처리 엔진의 재현성 검사이며 독립적인 체결 모형이나 수익성 검산이 아니다.

이번 결과는 **개별 시점의 적격성**을 기록한다. 관찰 사이에 발생한 장애까지 포함한 연속 교집합 구간을 인증하지 않는다. [전진 자료 계약](FORWARD_DATA_CONTRACT_V1.md)의 하루/시간대 적격 비율·최장 공백 판정으로 바로 올리지 않는다.

[추가 관측 이력](../../reports/validation/durable_market_feed_v2_20260917/inspection_record.json)을 남겼다. 다음 전진 구간 등록 때 이전 모든 관측 이력과 합쳐야 한다. 동결된 정책 템플릿의 `last_inspected_end_utc`가 이번 관측까지 자동 갱신된 것으로 간주하면 안 된다.

## 재현과 다음 순서

표준 라이브러리 검사와, 기존 websockets 환경의 짧은 공개 수집:

```bash
python3 -m unittest tests.test_durable_market_feed
.venv/bin/python scripts/probe_durable_market_feed.py --output reports/validation/NEW_UNIQUE_DIRECTORY --seconds 12
```

새 출력 경로만 허용하며 관찰 창은5~20초다. 장시간 실행/자동 재시도/실주문 인터페이스가 아니다. 중간 실패와 원본을 남기고 종료한다.

다음은 **이 통합 경로에서의 연결 단절·프로세스 종료·감사 기록 유실 시험과, 연속 적격 구간 생성**이다. 그 뒤 유한 재연결 예산·원래 종료 시각 유지·용량 검증을 연결해24시간 기술 시험의 등록 가능성을 판단한다. 아직은 해당 등록을 차단하며 전략·계정 조건·체결 모형의 미완료도 그대로 남아 있다.
