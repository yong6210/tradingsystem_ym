# 계좌 공통 청산 예약·대조 v1

2026-09-17. **일반 시장가 전환과 보호 청산의 중복 수량 사용을 막는 오프라인 연결을 완료했다.** 계좌 전체 자동매매 시스템이나 실거래 연결의 완료는 아니다. 이전 단계의 동결된 두 디스패처는 수정하지 않고 공통 예약기와 연결 계층을 추가했다.

## 문제와 결과

이전에는 두 경로가 각자 `.003 BTC` 포지션을 보고 `.003 BTC` 청산을 계획할 수 있었다. 각 원장 내부의 중복 방지는 다른 원장의 예약까지 알지 못한다.

이제 계좌/종목/운영 구간별 SQLite 예약기를 공유한다. 한 경로가 송신 전에 공통 예약을 커밋하면, 다른 경로는 해당 주문의 상태가 전체 계좌 관측에 반영될 때까지 추가 수량 송신이 차단된다. 주문을 확인한 후에는 알려진 미체결 청산 수량을 한 번만 차감한다. 시장가 응답 성공 자체로 예약을 해제하지 않는다. 일반 시장가 전환의 원 주문 종료 상태·원 수량·누적 체결·방향은 계좌 관측과 기존 로컬 원장 사이에서도 일치해야 한다.

예: 일반 청산 `.003` 중 `.001`만 체결 후 만료 → 현재 포지션 `.002`와 누적 체결 `.001`이 일치하는 새 전체 관측 → 공통 예약 해제 → 기존 보호 청산 `.003` 계획 폐기 → 새 보호 청산 `.002`만 송신.

## 연결 계약

- `AccountView`: 동일한 account/symbol/epoch, 증가하는 조정 버전, 관측 시각, 부호 있는 포지션, 전체 주문 목록. 버전은 거래소 timestamp가 아니라 조정기가 부여한 순서다.
- `AccountOrder`: 원 주문 ID, ENTRY/EXIT/STOP, 방향, 원 수량, 누적 체결, 상태, 주문별 조정 버전, 명시적 reduce-only. 이 운영 구간에서 이미 관측한 종료 주문도 목록에 유지한다.
- **포지션 변화 = 모든 알려진 주문의 부호 있는 누적 체결 증가분 합.** 새 주문은 이전 누계를 0으로 본다. 첫 관측의 포지션은 기준점이며 그 이전 거래를 재구성하지 않는다.
- 누락된 기존 주문, 바뀐 주문 정체성, 누계/버전 역행, 동일 버전 상충, 종료 주문 재개, 포지션 불일치는 계좌 조정 중단 사유로 영속화한다. 실패 뒤 직전의 정상 스냅샷을 재사용하여 송신할 수 없다.
- 신선도는 기존 연구 가정과 같은 1초다. 잘못되거나 오래된 관측이 제출되면 중단이 유지된다. 자동 복구/초기화 명령은 제공하지 않는다.
- `BEGIN IMMEDIATE` 안에서 전체 잔량과 기존 예약을 확인하고 새 예약을 커밋한다. 두 SQLite 연결의 동시 경쟁 검사에서 한 예약만 성공했다.
- 예약 뒤 로컬 원장 점유 전에 종료되면 예약을 보존하고 불명 상태로 남긴다. 예약이 없었던 것처럼 재송신하지 않는다. 두 DB가 하나의 트랜잭션인 것처럼 주장하지 않는다.
- 로컬 디스패처가 전송 전에 거절했고 transport 호출이 없었다는 실행 증거가 있을 때만 미송신 예약을 해제한다. 타임아웃/조회 없음/예외/프로세스 종료는 미송신 증거가 아니다.

예약의 `released` 값은 0=확인 대기, 1=새 계좌 관측의 종료 주문/포지션으로 해제, 2=연결 계층이 입증한 미송신이다. 2만 같은 불변 명령의 재승인을 허용한다. 중복 ID를 다른 경로나 수량에 재사용하는 것은 거부한다.

## 기존 경로와의 관계

[일반 fallback](../../app/research/execution/durable_fallback.py)과 [보호 조정기](../../app/research/execution/protection_coordinator.py)는 각각 자신의 예약·응답·체결 원장을 계속 보유한다. [새 연결 계층](../../app/research/execution/account_exit_bridge.py)은 이들 위에서 공통 예약을 선행한다. 응답 불명/접수 이후 재시작은 기존 ID 조회 경로로만 복구한다.

보호 경로의 오래된 READY 명령이 새 포지션보다 크면, 현재 감독 요구와 버전을 확인한 뒤 로컬 트랜잭션으로 `SUPERSEDED` 처리하고 감사 기록을 남긴다. 이를 생략하면 공통 예약기가 큰 수량을 계속 거부하여 잔량 재계획 자체가 막힌다. 보호 원장 스키마를 직접 사용하는 이 연결 지점은 현재 소스 버전과 결합되어 있으며 회귀 테스트 대상으로 관리한다.

이 통합은 **청산 예약 범위**다. fallback의 신규 진입 시장가 명령은 `ENTRY_RISK_RESERVATION_NOT_IMPLEMENTED`로 거부한다. 진입 위험·증거금·수수료 예산의 공통 예약은 아직 없다. 기존 위험/필터 재승인 콜백은 여전히 필요하며, 공통 수량 예약이 이를 대신하지 않는다. 취소·조회는 수량을 추가하지 않으므로 기존 경로를 사용한다. 모든 관련 청산은 같은 계좌 예약기를 거쳐야 하며, 예전 디스패처를 직접 호출하는 우회 경로가 활성화된 실환경은 지원하지 않는다.

## 검증

[검증 기록](../../reports/validation/account_exit_arbitration_20260917/verification.json), [관련 테스트 로그](../../reports/validation/account_exit_arbitration_20260917/tests.log), [7단계 통합 훈련](../../reports/validation/account_exit_arbitration_20260917/rechecked_drill/drill.json).

- 신규 30개 포함 관련 296개 테스트 통과. 일반 청산→비상 청산 및 반대 순서 모두 같은 잔량에 실제 모의 송신 한 건만 허용했다.
- 모의 훈련은 `.003 BTC` 부분 청산 응답 유실, 다른 경로 차단, 재시작/기존 ID 조회, `.001` 체결 대조, 오래된 보호 계획 폐기, `.002` 잔량 청산, flat 대조 순서다.
- 모의 주문 2건. 두 로컬 원장 체결 합 `.003 BTC`, 별도 모의 거래소 DB 체결 합 `.003 BTC`, 최종 포지션 0으로 일치했다.
- 실제 자식 프로세스를 공통 예약 직후와 모의 접수 직후 강제 종료했다. 전자는 불명 예약 보존/송신 0건, 후자는 조회 복구/송신 1건이었다.
- 포지션 불일치 이후 재시작, 중복/역순/누락 주문, 잘못된 계좌, 서로 다른 DB 연결의 예약 경쟁을 검사했다.
- 실주문·개인 API 요청·외부 통지 0. 훈련 체결은 지정한 응답이며 성과나 실제 체결률의 증거가 아니다.

| 항목 | 현재 한계 | 다음 확인 |
|---|---|---|
| 활성 손절과 즉시 시장가 청산 | 조건부 STOP도 수량을 예약하므로 부족하면 차단. 확인된 손절 취소 뒤에만 수량이 풀림 | 취소 중 손절 체결·응답 유실·보호 공백을 포함한 별도 전환 상태기계. 단순히 STOP 예약을 빼서 통과시키지 않음 |
| 실제 조정 데이터 | 테스트가 완전한 계좌 관측을 제공. 자체 REST/스트림 조정기는 없음 | 주문·체결·포지션 관측 시점의 차이, 누락/늦은 이벤트를 포함하는 조정 생산기 |
| 수량 보존 검사 한계 | 첫 기준점 이전 오류, 관측되지 않은 상쇄 거래, 수수료/현금/증거금은 검출 불가 | 초기 계좌 증거 및 체결·현금·비용 원장 대조 |

| 진입과 위험 예산 | 공통 청산 수량만 구현 | 계좌 공통 진입 위험·증거금·다중 주기 예약 |

다음 운영 작업은 **활성 손절에서 비상 청산으로 전환하는 취소/체결 경합 계약**이다. 연구 자료 쪽은 **L2 재생·공백/재연결 검사**가 남는다. 이 작업으로 전략 선택·백테스트 비용·기존 결과는 변경하지 않았다.
